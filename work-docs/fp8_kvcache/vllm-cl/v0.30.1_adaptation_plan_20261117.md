# FP8 KV Cache 在 vLLM v0.30.1 分支的适配方案

日期：2026-11-17

## 1. 结论先行

1. 旧 FP8 KV cache 工作实际上只改在 `vllm-cl`：`vllm:fp8-kvcache-main` 相对
   `vllm:main` 没有额外提交。旧实现是 `vllm-cl:fp8-kvcache-main` 上的单个提交
   `a3cf83b`（基于 `9563a8b`），目标模型是 Qwen3 GQA、`D=128`、`P=256`。
2. 新基线 `vllm:fp8-cache-v0.30.1` / `vllm-cl:fp8-cache-v0.30.1` 已包含上游
   `fp8_per_token_head` 的 `KVQuantMode`、`AttentionSpec` 和 allocator 框架，
   但 DLC attention backend 还没有声明支持它，也没有对应的 cache shape/写入/
   读取路径。
3. 旧 Python 原型不能直接 cherry-pick：它依赖旧版 backend API、逐请求 Python
   SDPA、逐 token `copy_`，且要求 `2*Hkv*128` 为 512B 整数倍（TP<=4）。新设计
   应改为“上游 spec + DLC raw page + 融合 writer + 融合 attention”的路径，可直接
   覆盖 TP8（每 rank 1 个 KV head）。
4. 本次已把两个远端算子分支合入本地：
   - kernel：`origin/heiqi_feat_8272_261103` → `DLC_Custom_Kernel:fp8-cache`
     （合并提交 `dd38ec1ff`）。
   - pytorch：`origin/heiqi_feat_2223_261103` → `pytorch:fp8-kvcache-main-2`
     （合并提交 `1f18e9ef11`）。
5. `reshape_and_cache_kv_fp8` 的 kernel 已在 `DLC_Custom_Kernel:main`（`5d03eff5d`），
   但 `vllm-cl` 还没有 C++ binding；GQA FP8 attention 也只有 pytorch 函数式接口，
   vLLM 侧仍需 wrapper 才能生产使用。
6. 上述 GQA FP8 算子不适用于 GLM-5.3 的 sparse MLA。GLM `D=512`、NoPE、4 个
   group scale、单侧 K/V 的 MLA 布局需要单独的 writer/reader 和 MLA attention
   适配，不能把 `D=128` GQA 算子直接套用。

## 3. v0.30.1 带来的关键变化

### 3.1 上游已有 FP8 per-token-head 量化模式

`vllm/vllm/v1/kv_cache_interface.py`：

- `KVQuantMode.FP8_PER_TOKEN_HEAD = 3`，字符串为 `fp8_per_token_head`。
- `AttentionSpec` 新增 `kv_quant_mode`、`num_head_slots`、`state_content_bytes`、
  `tokens_per_state`。
- `page_size_bytes = num_heads * num_states * state_content_size_bytes`。

`vllm/vllm/utils/torch_utils.py` 把 `fp8_per_token_head` 映射为 `torch.uint8`，
因此 DLC 侧最终 cache dtype 应优先保持 `uint8`，不要依赖旧的 `float8_e4m3fn`
公开容器。

### 3.2 backend 需要主动“打包”spec

`vllm/vllm/v1/attention/backend.py::customize_spec` 是 v0.30.1 新增的打包入口。
Triton backend 用它把 per-token-head 的 scale 折进每个 head slot：

```python
state_content_bytes = (head_size + head_size_v) * dtype_size + 2 * 4
```

对 DLC GQA `D=128`、`Hkv` 个 KV head：

```text
state_content_bytes = (128 + 128) * 1 + 8 = 264
page_bytes = block_size * Hkv * 264
```

TP4（`Hkv=2`）时为 `256 * 2 * 264 = 135168` B；TP8（`Hkv=1`）时为
`256 * 1 * 264 = 67584` B。两者都是 512B 的整数倍，满足 DLC 一字节 tensor
的物理对齐要求，因此融合路径不需要旧原型“每 token 512B”限制。

### 3.3 backend 选择会检查 per-head quant 能力

`AttentionBackend.get_invalid_reasons` 会检查
`supports_per_head_quant_scales()`。DLC backend 必须显式返回 `True`，否则
`--kv-cache-dtype fp8_per_token_head` 会在 backend 选择阶段被拒绝。

### 3.4 allocator/runner 仍按 backend 的 shape 建 cache

新 runner 在 `_reshape_kv_cache_tensors` 中调用
`attn_backend.get_kv_cache_shape(...)`，并可能调用
`get_kv_cache_block_dim(...)`。DLC backend 应为 FP8 返回
`(num_blocks, page_bytes)`，block dim 返回 0；非 FP8 路径保持现有
`(B,H,N,2C)` / `(2,B,H,N,C)` 语义。

## 4. 目标布局与 ABI

以 TP4、`Hkv=2`、`B=256` 为例：

```text
token_value_bytes   = 2 * Hkv * 128 = 512
token_scale_bytes   = 2 * Hkv * 4   = 16
values_region_bytes = 256 * 512     = 131072
scales_region_bytes = 256 * 16      = 4096
page_bytes          = 135168
```

页内布局固定为：

```text
[ values: B * 2H * 128 ][ scales: B * 2H * 4 ]

values: [K0..K(H-1), V0..V(H-1)]，按 token 连续
scales: [sK0..sK(H-1), sV0..sV(H-1)]，按 token 连续，FP32 原始 bit
```

这与 `DLC_Custom_Kernel/dlc_kernels/kvcache/reshape_and_cache_kv_fp8.cpp`
及 `pytorch` 的 `dlc_flash_attn_varlen_gqa_fp8` 完全一致。

## 5. vllm-cl 适配设计

### 5.1 cache spec / allocator

在 `TorchAttentionBackend` 中增加：

```python
from vllm.v1.kv_cache_interface import KVQuantMode

class TorchAttentionBackend(AttentionBackend):
    supported_kv_cache_dtypes = [
        "auto", "float16", "bfloat16", "fp8_per_token_head",
    ]

    @classmethod
    def supports_per_head_quant_scales(cls) -> bool:
        return True

    @classmethod
    def customize_spec(cls, spec):
        if spec.kv_quant_mode != KVQuantMode.FP8_PER_TOKEN_HEAD:
            return spec
        scale_bytes = 2 * 4
        content = (spec.head_size + spec.head_size_v) + scale_bytes
        return replace(spec, state_content_bytes=content)

    @staticmethod
    def get_kv_cache_shape(num_blocks, block_size, num_kv_heads,
                           head_size, cache_dtype_str="auto", **kwargs):
        if cache_dtype_str == "fp8_per_token_head":
            return (num_blocks,
                    block_size * num_kv_heads * (2 * head_size + 2 * 4))
        ...

    @staticmethod
    def get_kv_cache_block_dim(block_size, num_kv_heads, head_size,
                               cache_dtype_str="auto"):
        if cache_dtype_str == "fp8_per_token_head":
            return 0
        ...
```

同时修改 DLC patch：

- `patch_kv_cache_interface.py::_page_size_bytes_padded`：FP8 per-token-head
  直接返回 `self.page_size_bytes`，不再走 BF16/FP32 的 head padding。
- `patch_kv_cache_utils.py::_dlc_physical_page_size_bytes`：FP8 per-token-head
  返回 `spec.page_size_bytes`。
- `_get_kv_cache_shape_for_dlc`：FP8 per-token-head 返回
  `(num_blocks, attn_spec.page_size_bytes)`。
- `worker/dlc_model_runner.py::_reshape_kv_cache_tensors`：FP8 模式下
  `raw_tensor.view(torch.uint8).view((num_blocks, page_bytes))`，不要走
  `permute/contiguous` 的 BF16 合并布局。

### 5.2 融合写入路径

kernel `custom_reshape_and_cache_kv_fp8` 的 ABI 是：

```text
key/value:    [T, Hkv, 128] BF16（DLC 下每个 token/head 源行 512B 对齐）
kv_cache:     [num_blocks, page_bytes] uint8
slot_mapping: int64[T]，-1 跳过
block_size:   int32
```

目前 `vllm-cl/csrc/cache.cpp` 只有 `reshape_and_cache`，需要新增：

```cpp
void reshape_and_cache_kv_fp8(at::Tensor& key, at::Tensor& value,
                              at::Tensor& kv_cache, at::Tensor& slot_mapping,
                              int64_t block_size) {
  auto k = at::dlc::KernelDesc();
  k.input(key);
  k.input(value);
  k.input(slot_mapping);
  k.output(kv_cache);
  k.scalar(static_cast<int>(block_size));
  k.launch("custom_reshape_and_cache_kv_fp8");
}
```

并在 `cache.h`、`torch_bindings.cpp`、`vllm_cl/_custom_ops.py` 注册
`reshape_and_cache_kv_fp8`。`slot_mapping` 若 `storage_offset()!=0` 要先 clone，
与现有 `reshape_and_cache`  wrapper 保持一致。

### 5.3 融合 attention 路径

`pytorch` 已提供：

```python
out, lse = torch.dlc_flash_attn_varlen_gqa_fp8(
    query,                # [Tq, Hq, 128] BF16
    fp8_cache,            # [num_blocks, page_bytes] uint8
    cu_seqlens_q,         # int32[B+1]
    seqused_k,            # int32[B]
    block_table,          # int32[B, max_blocks]
    max_seqlen_q,
    max_seqlen_k,
    block_size,           # 必须 256
    num_kv_heads,
    softmax_scale,
    causal,
)
```

在 `vllm_cl/_custom_ops.py` 增加 `flash_attn_varlen_gqa_fp8` wrapper，并在
`TorchAttentionBackendImpl.forward` 的 FP8 分支：

1. 调用 `reshape_and_cache_kv_fp8` 写入本步 K/V（`kv_sharing` 时跳过）。
2. 调用 `torch.dlc_flash_attn_varlen_gqa_fp8`。
3. 把返回的 `out [Tq,Hq,128]` copy 到 vLLM 的 `output [Tq,Hq*128]`。
4. 如需 LSE，继续使用 `[Hq,Tq,1]` 的现有约定。

这一步会完全取代旧原型的逐请求 `F.scaled_dot_product_attention` 和逐 token
`copy_`，是进入 graph/生产 decode 的前提。

### 5.4 旧原型代码的复用边界

- `fp8_gqa_kv_cache.py` 的布局计算、slot 校验、`copy_blocks`/`zero_blocks`
  可以保留作为 reference/调试路径。
- `quantize_and_scatter` / `gather_blocks` 不应进入生产 forward；生产路径改用
  融合 writer + 融合 attention。
- 旧原型要求 cache dtype 为 `float8_e4m3fn`；新路径建议 cache 本体保持
  `uint8`，只在量化临时张量上使用 `float8_e4m3fn`，避免与上游
  `fp8_per_token_head -> uint8` 映射冲突。
- 旧原型拒绝 `2*Hkv*128 % 512 != 0`；新融合 kernel 只要求整页对齐，应删除
  该限制以支持 TP8。

## 6. 验证矩阵

### 6.1 算子级

- `custom_reshape_and_cache_kv_fp8`：`T=0/1/尾 token`、`Hkv=1/2/4/8`、
  `block_size=256`、乱序/跨页/重复/`-1` slot、NaN/Inf/±0。
- `custom_flash_attention_varlen_GQA_fp8`：decode、full prefill、chunked prefill、
  混合 varlen batch、causal、非连续 block table、尾页、`seqused_k` 变长、
  双 XYS、graph replay。
- 与 CPU reference 对齐：`atol=2e-2, rtol=2e-2`；LSE `1e-2/1e-2`。

### 6.2 vLLM 端到端

- Qwen3-32B-Mix，TP4 / TP8，`--kv-cache-dtype fp8_per_token_head`。
- 同显存预算下 block/token 容量应为 BF16 的约 `1.939x`。
- 短请求与 8192-token needle 精度对照；prefix cache、chunked prefill、
  `FULL_DECODE_ONLY` graph。
- 关注 `seqused_k==0` 的 dummy/warmup 请求、FP8 cache NaN、block 0 污染。

### 6.3 回归

- BF16 merged KV cache 路径不变。
- `fp8`（per-tensor）路径仍应被明确拒绝，避免误走 per-token-head ABI。
- TP8 不再因 512B token 限制回退。

## 7. 风险与边界

1. **GLM sparse MLA 不在本方案覆盖范围**。GLM 需要 `D=512`、4 个 group、
   单侧 K/V、NoPE 的 MLA 布局；当前 `#8271/#8272` 是 `D=128` GQA ABI。
2. **pytorch 函数式接口与 issue 签名有差异**：issue 建议传入 `out`/`softmax_lse`
   并返回 `None`；当前合并实现是分配并返回 `(out,lse)`。vLLM 接入需要额外 copy，
   或在 pytorch 侧增加 out 变体。
3. **`enabled_kernels.hpp` 是生成文件**：新 kernel 需要在 kernel 仓构建时由
   `dlc_src/gen.py` 重新生成并安装到 `/usr/local/chipltech/synapse/include/`，
   否则 pytorch 编译会报 `custom_flash_attention_varlen_GQA_fp8` 不存在。
4. **未完成全量构建/真机验证**：本次只做了 kernel clang 编译和 pytorch
   `FusedOps.cpp` 对象编译；`libcustom_dlc_perf_lib.so`、`libtorch_dlc.so`
   尚未重建，DLC 真机测试尚未执行。
5. **旧原型不是性能路径**：Python 逐 token copy/逐请求 SDPA 只能用于
   correctness bring-up，不能作为生产实现。

## 8. 建议落地顺序

1. 在 `DLC_Custom_Kernel` 重建并安装 kernel 库，确认
   `enabled_kernels.hpp` 含 `custom_flash_attention_varlen_GQA_fp8`。
2. 重建 pytorch DLC 扩展，确认 `torch.dlc_flash_attn_varlen_gqa_fp8` 可调用。
3. 按第 5 节改 `vllm-cl`：spec/allocator → C++ writer binding → fused attention
   wrapper → backend FP8 分支。
4. 先跑 Qwen3 TP4 correctness，再跑 TP8、prefix cache、graph 和 8192-token。
5. GLM sparse MLA 另开分支，按 `glm53_sparse_mla_fp8_plan_20261027.md` 设计
   `D=512` writer/reader 与 MLA attention，不复用 GQA 页布局。
