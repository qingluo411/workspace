原 MHA/GQA 分支

输入 BF16 Q/K/V；K8、V8 分别使用 sK、sV。PV 概率 tile 转 BF16，输出累加器保持 FP32，最终输出 BF16。

GLM MLA/DSA 分支 · 待定义

缓存 norm 后的 latent 和 RoPE 后的 positional key。DSA 读取选中的 slots，在片上恢复 BF16，复用 BF16 计算结构。

Q 保持 BF16；禁止把整份历史 cache 反量化成第二份 HBM BF16 镜像。局部有界 scratch 与原模型既有 prefill workspace 需单独说明。

上游 Triton 在非 FP8 Q 路径执行 decode×scale→Q dtype，为该原则提供依据；DLC 的具体布局和精度仍需自身验证。官方实现

对齐术语本目标config的self_attn跳过权重量化，W4用于其余指定模块；不能把整个W4模型说成每个投影均4bit。“读回来用 BF16 算”不能恢复 FP8 已丢失的信息。FP32 softmax 和累加不表示等同全 FP32 reference。GLM latent同时影响key评分和值聚合，不能机械复用独立K/V尺度。

09 / COMPILER CONTRACT

x / scale 不保证得到规范中的 RN32 除法。

10 / 18

LLVM DLC LowerFdiv：reciprocal(divisor) → FMUL。即使倒数自身正确舍入，最终 FP8 code 仍可能跨过中点。

BF16 x = 1.0078125
FP32 s = 1.4021739959716797

路径FP32 结果FP8 code
RN32(x / s)0.71874994040x33
RN32(x × RN32(1/s))0.718750x34

独立主机验证通过；不是 TYD 实测。差异发生在 FP8 normal 区间。

必须冻结的三项约定

  • 写入以“最终 FP8 code 符合 reference”为目标；评估精确除法或带边界修正的实现及其成本。
  • scale 不应只校验“有限且正”：补充极小尺度、乘法下溢和 FTZ 的处理。
  • BF16 NaN 明确只要求 isnan，或用软件统一 payload；不要误要求 intrinsic 输出固定 0x7fc0。
模拟器 pack.f16 的正常数使用 RNE，但 FP32 subnormal 会清零，NaN 可能形成 BF16 0x7fc1。文档的通用位级 reference 尚未覆盖这组差异。
编译器 / 算子团队已有 fp32_div_high 可评估，但注释的 641 clocks/call 不是本次测量值，也不是性能保证。它仍有 subnormal 商处理，不能靠名字宣称任意 RN32 精确。此问题无需必然修改 LLVM，可以由融合量化 helper 修正；验收最终 code 才与 ABI 相关。

保留当前 BF16 indexer cache

DLC 实际 indexer 缓存是 BF16 D128，独立于主 latent cache。按现对齐推导：主缓存 1536→768 B 后，加 indexer 512 B，两类合计 2048→1280 B，仅省 37.5%。

覆盖所有实际读取分支

当前 MLA 还会分流 prefill MHA / MQA，prefix/chunked 会读取历史。必须一并改接 gather/read，或明确统一 sparse 路径并验收；只修稀疏 decode 不够。

方案负责人这是修订建议，接口名、布局和 scale 策略都尚未冻结。现 sparse backend 仅auto/BF16，writer dtype/scale仍TODO，旧PyTorch writer强制同dtype。不能仅扩supported dtype列表。37.5%是主MLA+不变indexer的条件推导，前提为每层均有该indexer且按现512B pitch；不是整机实测。GLM5.1当前最小真实目标；5.2 MTP和5.3 KDA/KPool另立后续包。
