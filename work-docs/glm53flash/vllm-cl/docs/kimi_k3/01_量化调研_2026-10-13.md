# Kimi K3 适配 DLC：第一步「量化」调研（2026-10-13）

> 目的：参照 GLM-5.3-Flash 的适配流程（`docs/glm5_flash/`），对 Kimi K3 做第一轮摸底。
> 本轮只回答一个问题：**K3 需要什么量化、DLC 现在支持什么量化、网络上有没有现成可用的量化权重。**
> 不展开算子/图/内存等其它适配面（只在末尾列出与量化强耦合的风险）。

---

## 0. 结论摘要（TL;DR）

1. **Kimi K3 的原生量化是 MXFP4，不是 AWQ/FP8。** 官方 checkpoint（`moonshotai/Kimi-K3`）
   用 **MXFP4 权重 + MXFP8 激活**，并且是 **QAT（从 SFT 阶段就量化训练）**，不是 PTQ。
   config.json 里没有标准 `quantization_config`，权重以 `U8`（4-bit 打包）+ `BF16/F32` scale 存储。
2. **DLC 当前没有任何 MXFP4 / NVFP4 / 4-bit 浮点通路。** DLC 支持的 4-bit 是**整数仿射量化**：
   AWQ（非对称 uint4，带 zero point）和对称 W4A16（无 zero point），group `32/64/128/per-channel`，
   覆盖 dense Linear 和 fused MoE；另有 W8A16、block-128 FP8(E4M3) 的 quant/dequant 和 FP8 KV/indexer cache。
   `DLCPlatform.supports_fp8() == False`，所以 FP8 linear/MoE 主路径也没开。
3. **现成的量化权重有，但没有一个是 DLC 能直接吃的。** 网络上可拿到：
   - 官方 `moonshotai/Kimi-K3` —— MXFP4，~1.56 TB（96 个 safetensors，HF + ModelScope 都有）；
   - `nvidia/Kimi-K3-NVFP4` —— NVIDIA NVFP4（Blackwell 用）；
   - `sgl-npu/Kimi-K3-W4A8` / `Eco-Tech/Kimi-K3-w4a8` —— 昇腾 A3 的 ModelSlim **W4A8**（~1.49 TB）；
   - `Inferact/Kimi-K3-DSpark`、`modal-labs/Kimi-K3-DFlash`、`RadixArk/Kimi-K3-DSpark` —— 投机解码草稿模型，不是量化权重。
   **没有找到 AWQ / GPTQ / compressed-tensors 的 K3 权重。**
4. **因此 K3 上 DLC 的量化路线只有三种**：
   (a) 给 DLC 新增 MXFP4 dequant + GEMM/MoE（工作量大，且 torch 2.5 连 `float8_e8m0fnu` 都没有）；
   (b) 离线把 K3 从 MXFP4 反量化后重新 PTQ 成 AWQ/W4A16（要有 ~5.6 TB BF16 级别的一次性算力/存储）；
   (c) 用同族的小模型（如 `Kimi-Linear-48B-A3B-Instruct`）先跑通架构，量化后置。
   详见 §5。

## 2. Kimi K3 到底需要什么量化

### 2.1 官方方案：MXFP4 权重 / MXFP8 激活（QAT）

官方 README §4 原文：

> Kimi K3 applies quantization-aware training from the SFT stage onward,
> using **MXFP4 weights with MXFP8 activations** for broad hardware compatibility.

要点：

- **MX 格式（OCP Microscaling）**：元素是 4-bit 浮点 **E2M1**；每个 block（通常 **32 个元素**）共享一个
  **E8M0**（8-bit 纯指数）scale。激活同理走 MXFP8（E4M3/E5M2 + E8M0 block scale）。
- 因为是 **QAT**，权重不是「先训 BF16 再 PTQ」，而是训练时就在 MXFP4 里收敛的；
  这使它的 MXFP4 精度明显好于事后 PTQ，但也意味着**不能简单地把它当作普通 BF16 模型重新量化**而期待等价结果。
- ModelScope 实测：`model-*-of-000096.safetensors`，`tensor_type = ['U8','BF16','F32']`——
  `U8` 就是 4-bit 打包数据（2 值/字节），`BF16/F32` 是 block scale 与非量化张量。
- 实际体积 ~1.56 TB（2.78T 参数 / 4.5 bit 左右）。qk_rope 等少量部件仍是 BF16。
- `config.json` 里 **没有** 标准 vLLM `quantization_config` 字段（`null`），
  说明这是「格式即量化」的 checkpoint：vLLM 靠权重 dtype/自定义 loader 识别（recipe 里称其为 “MXFP4 checkpoint”）。

### 2.2 上游跑 MXFP4 的方式（供对照）

- **vLLM recipe**（`recipes.vllm.ai/moonshotai/Kimi-K3`）：用 `vllm/vllm-openai:kimi-k3` 镜像
  （CUDA 13 构建），推荐 TP8 / TEP16 / PP2 / PD 分离等拓扑。
- **SGLang cookbook**：B200 用 `flashinfer_mxfp4`，**H100/H200 退到 Marlin**；另提供
  `nvidia/Kimi-K3-NVFP4`（走专门的 nvfp4 镜像）与昇腾 `Kimi-K3-W4A8`。
- 也就是说上游至少实现了三条 4-bit 浮点/MX 通路：MXFP4（Blackwell/NPU）、NVFP4（NVIDIA）、W4A8（昇腾）。
  **DLC 三条都没有。**

### 2.3 K3 对量化的「硬约束」

| 约束 | 说明 |
|---|---|
| 权重格式 | MXFP4（E2M1 + E8M0 block-32）。DLC 无此格式。 |
| 激活精度 | MXFP8（E4M3/E5M2 + E8M0 block-32）。DLC 无此格式，且 `supports_fp8=False`。 |
| 非量化部件 | attention/KDA/norm/router/vision/embedding 等需保持 BF16/FP32（和 GLM5 的 `modules_to_not_convert` 同理，K3 用 `latent_moe_use_norm`、`mla_use_output_gate` 等）。 |
| Scale 类型 | E8M0 —— 当前 venv 的 `torch 2.5` **没有 `torch.float8_e8m0fnu`**（`vllm_cl/__init__.py` 里显式把它别名成了 `bfloat16`）。这是 MX 通路的第一道坎。 |
| 规模 | 2.78T 参数、~1.56 TB（4-bit）。8 卡 TYD（~60 GB/卡可用）**装不下**，必须多机多卡；量化/转换本身也需要 TB 级的内存与磁盘。 |

## 3. DLC 现在支持哪些量化方法

### 3.1 一句话

DLC 目前是「**整数仿射 4/8-bit 权重 + BF16 激活（W4A16 / W8A16）**」路线，外加
block-128 FP8 的**辅助算子**（quant/dequant、KV/indexer cache），以及 `compressed-tensors`
的 pack 布局转换。它**没有** 4-bit 浮点（MXFP4/NVFP4）通路。

### 3.2 具体能力清单（代码实证）

| 能力 | vLLM 插件入口 | DLC kernel / pytorch op | 状态 |
|---|---|---|---|
| **AWQ W4A16 dense** | `DLCAWQMarlinLinearMethod`（`vllm_cl/ops/awq_marlin.py`）→ `awq_gemm` | `awq_gemm_g{32,64,128}_ah_*`、`awq_gemm_per_channel_ah_*`；op `awq_gemm` / `awq_gemm_col_major` | ✅ 正在用（GLM-5.3-Flash-Mix 就是它） |
| **AWQ W4A16 MoE** | `DLCAWQMarlinMoEMethod.apply_monolithic` → `dlc_vllm_fused_moe_w4a16_awq_col_major` | `custom_vllm_fused_moe_w4a16_col_major_g{32,64,128}[_actorder_dynamic][_align][_decode]` | ✅ 正在用 |
| **对称 W4A16 MoE**（无 zero point，GPTQ/compressed-tensors 风格） | 尚无插件 wiring | `custom_vllm_fused_moe_w4a16_sym_col_major_g{32,64,128}[_actorder_dynamic]` | 🟡 kernel 有，未接 |
| **W8A16 dense** | 尚无插件 wiring | `w8a16_gemm_ah_*`、`mm_w8a16*` | 🟡 kernel 有，未接 |
| **W8A16 MoE（awq / sym）** | 尚无插件 wiring | `custom_vllm_fused_moe_w8a16_{awq,sym}_col_major_g{32,64,128}` | 🟡 kernel 有，未接 |
| **AWQ 布局转换** | `process_weights_after_loading` | `awq_uint4_to_dlc_uint4`、`awq_uint4_to_dlc_uint4_colpack`、`dlc_to_col_major_awq`、`awq_w1_scale_preprocessing` | ✅ |
| **compressed-tensors pack-quantized (W4/W8)** | `vllm_cl/ops/compressed_tensors_layout.py` | `compressed_tensors_pack_to_rowpack_{w4,w8}`、`compressed_tensors_uint4_zero_point_to_dlc_{rowpack,colpack}` | 🟡 布局转换已实现，端到端接线有限 |
| **block-128 FP8 (E4M3) quant/dequant** | 无（仅底层） | `quant_e4m3_g128`、`dequant_e4m3_g128_bf16`、`dequant_e5m2_g128_bf16`；op `dlc_quant_e4m3` | 🟡 辅助用途 |
| **FP8 KV cache / indexer cache** | `init_fp8_kv_scales`、`dlc_indexer_k_quant_and_cache` | `indexer_k_quant_and_cache_bf16`、`cp_gather_indexer_k_quant_cache` | 🟡 仅 KV/indexer |
| **FP8 linear / MoE 主路径** | `DLCPlatform.supports_fp8()` = **False** | — | ❌ 未开放 |
| **MXFP4 / NVFP4 / 任意 4-bit 浮点** | 无 | 无 | ❌ |
| **BF16（非量化）基线** | 默认 | `mm/matmul` bf16 系列 | ✅ |

> 提示：`pytorch` 侧相关 op 有 `dlc_vllm_fused_moe_w4a16_awq_col_major`、
> `dlc_vllm_fused_moe_w8a16_awq_col_major`、`dlc_quant_e4m3`、`dlc_awq_w1_scale_preprocess`、
> `awq_uint4_to_dlc_uint4(_colpack)`、`dlc_to_col_major_awq` 等，均已在主分支编译产物中确认存在。

### 3.3 GLM-5.3-Flash 是怎么用的（直接先例）

GLM-5.3-Flash 官方 checkpoint 是 **block-FP8**，但 DLC `supports_fp8=False`，
所以实际部署用的是自备的 **AWQ 4-bit 混合权重** `/mnt/jfs/models/GLM-5.3-Flash-Mix`
（120 个 safetensors、~184 GB、`--dtype bfloat16`）。
`vllm_cl/ops/awq_marlin.py` 里的两个坑（qzeros 用专用 `awq_uint4_to_dlc_uint4_colpack`、
`swiglu_limit` 不能写死）都是为它修的。见
`docs/glm5_flash/GLM-5.3-Flash_vLLM-CL_联调问题与修复记录.md`、`阻断点2-7.md`。

**结论：DLC 上目前唯一的成熟量化路线 = W4A16（AWQ 为主）。**

## 4. 怎么做量化（DLC 视角的可操作流程）

### 4.1 产出 W4A16 权重（离线，在 x86 + GPU 上做）

推荐 **`llm-compressor`**（vLLM 官方，AutoAWQ 已 deprecated，被其 AWQ 示例取代）：

```bash
pip install llmcompressor   # 与 vllm 分环境
```

- **AWQ（非对称，带 zero point）→ DLC 首选**：
  `llm-compressor/examples/awq/` 流程；`scheme = W4A16`，`group_size=128`（DLC 也支持 32/64/per-channel），
  校准数据用与线上分布接近的样本。
- **GPTQ / compressed-tensors 对称 W4A16（可选）**：DLC 有 `..._w4a16_sym_...` MoE kernel 和
  `compressed_tensors_pack_to_rowpack_*`，但插件端 wiring 不完整，优先级低于 AWQ。
- **W8A16（可选）**：kernel 齐全（`w8a16_gemm`、`..._w8a16_{awq,sym}_...`），但同样未接插件。

必须维护 **`modules_to_not_convert`（排除列表）**：KDA、attention、norm、router、embedding、
vision tower、以及各种 `*_proj`/`*_conv1d` 这类小张量不参与量化（GLM5 的排除表有 1509 项）。

### 4.2 在 DLC 上加载（运行时）

```bash
vllm serve <W4A16 ckpt> \
  --quantization awq \          # vllm_cl monkeypatch 把 AutoAWQConfig 换成 DLCAWQMarlinConfig
  --dtype bfloat16 \
  --block-size 256 \            # DLC 强制
  --enforce-eager \
  --tensor-parallel-size <TP>
```

加载期 DLC 会自动做布局转换：

```text
AWQ checkpoint (qweight/qzeros/scales)
  → awq_uint4_to_dlc_uint4 / _colpack       # 权重/零点打包
  → dlc_to_col_major_awq                    # 列主序（col-major）
  → awq_gemm / dlc_vllm_fused_moe_w4a16_awq_col_major
```

### 4.3 关键注意事项

1. **group_size 与 ah（activation hidden）形状必须命中 kernel 模板**：DLC 的 dense AWQ/W8A16 GEMM
   是按 hidden 宽度展开成一批 `ah_*` 固定形状 kernel 的；K3 的 hidden=7168、latent=3584、
   moe_intermediate=3072、q_lora=1536、kv_lora=512 —— 需逐个核对模板是否覆盖（GLM5 是 4096 系）。
2. **fused MoE 的张量形状约束**：`qzeros` 必须是 colpack 布局（`[num_groups, ceil(packed_cols/128)*128]`）。
3. **router/激活的精度**：K3 router 是 sigmoid + 16/896 + renormalize；DLC fused MoE 要求 bf16 gating input，
   与 GLM5 一样存在「FP32 router 目标 vs BF16 现实」的取舍。
4. **SiTU-GLU**：K3 的激活是 `situ`（beta=4/25），DLC fused MoE 只有 silu / swiglu(clamp) 等；
   量化前先确认激活实现方式（这会影响量化排除/融合策略）。
5. **torch 版本**：venv 是 torch 2.5.0，很多新 quant 元数据（E8M0、MX 相关注册）缺失，
   插件已用别名兜底，但这也说明 DLC 短期不可能直接吃 MXFP4。

## 6. 差距分析与可选路线

| 路线 | 做法 | 工作量 | 风险 |
|---|---|---|---|
| **A. DLC 新增 MXFP4** | 实现 E2M1 反量化 + MX 分块 GEMM/MoE；加载器支持 `U8`+`E8M0`；补齐 `float8_e8m0fnu` | 很大（新数据类型 + 新 GEMM/MoE kernel + loader） | torch 2.5 缺 E8M0；DLC 硬件是否有 4-bit 浮点支持未知；收益不确定 |
| **B. 离线转 AWQ/W4A16** | 从官方 MXFP4 反量化 → BF16 → 用 llm-compressor PTQ 成 AWQ W4A16 | 一次性算力/存储很大（BF16 中间态 ~5.6 TB），但**完全复用现有 DLC 通路** | QAT 模型再 PTQ 的精度损失需评估；转换脚本要处理 96 分片/自定义建模代码 |
| **C. 先小后大（推荐起步）** | 用同族小模型（`moonshotai/Kimi-Linear-48B-A3B-Instruct`）先把 KDA+Gated MLA+MoE+SiTU-GLU 的架构在 DLC 上跑通并做 AWQ | 中 | 不能直接验证 2.8T 的量化行为，但能先把「非量化」的适配风险清掉 |
| **D. W4A8 ModelSlim 转 AWQ** | 从昇腾 W4A8 转 DLC W4A16 | 中（需要解析 ModelSlim 格式 + 反量化激活侧） | W4A8 的激活量化信息对 W4A16 无用，仍需 BF16 重标定 |

**建议**：把量化拆成两阶段 ——
**阶段一**：不碰 MXFP4，先用路线 C（小模型，纯 BF16/AWQ）验证 K3 架构在 DLC 的算子/图/内存可行性；
**阶段二**：在阶段一跑通后，对 K3 走路线 B（离线转 AWQ W4A16），或评估路线 A 的投入产出。

## 7. 与量化强耦合、需要一并确认的问题

1. **K3 的非量化部件边界**：哪些层/模块必须 BF16/FP32（KDA、MLA、router、vision、embedding、latent norm）？
   需要按 GLM5 的方式产出一份 `modules_to_not_convert` 等价清单。
2. **激活 SiTU-GLU 的落点**：dense/shared/vision FFN 与 routed expert 的激活分别怎么实现？
   这决定量化时哪些融合可以保留。
3. **规模与部署形态**：1.56 TB（4-bit）在 8 卡 TYD 放不下，量化路线必须和 TP/EP/PP/PD 拓扑一起定。
4. **能否拿到官方量化脚本**：K3 QAT 的量化 recipe 若官方有放出，路线 B 的精度损失会小很多。
5. **HuggingFace 直连**：本环境 `huggingface.co` 不可达（`hf-mirror.com` 只做重定向），
   后续拉权重需走 ModelScope 或代理。

## 附录 A：`Kimi-Linear-48B-A3B-Instruct` 和 K3 是不是同一套架构？

**不是同一套，但同源。** K3 的 `text_config` 直接声明 `architectures: ["KimiLinearForCausalLM"]`、
`auto_map -> modeling_kimi_linear.KimiLinearModel`，`model_type` 也都是 `kimi_linear`——
也就是说 **K3 的文本主干就是 Kimi-Linear 架构的放大版**；K3 在它之上又加了多模态与若干新模块。

### 共享的部分（KL 可作为 K3 的架构验证代理）

- **KDA（Kimi Delta Attention）**：`short_conv_kernel_size=4`、KDA `head_dim=128`；
- **混合布局**：KDA 与 full-attention(MLA) 按固定间隔交替（都是第 4 层为第一个 full-attn）；
- **MLA 核心**：`kv_lora_rank=512`、`qk_nope_head_dim=128`、`qk_rope_head_dim=64`、
  `v_head_dim=128`、`mla_use_nope=true`；
- **MoE**：sigmoid router、`moe_renormalize=true`、`use_grouped_topk=true`；
- 共同词表 163840、1M 上下文。

### 关键差异（K3 多出来的 / 不一样的）

| 字段 | Kimi-Linear-48B-A3B | Kimi K3 (text_config) | 影响 |
|---|---|---|---|
| 外层架构 | `KimiLinearForCausalLM`（纯文本） | `KimiK3ForConditionalGeneration`（**多模态**，MoonViT-V2） | KL 覆盖不到视觉塔 |
| `attn_res_block_size` | 无 | **12（Attention Residuals）** | K3 独有模块，KL 无 |
| `latent_moe_use_norm` | 无 | **true（Latent MoE, dim 3584）** | K3 独有 |
| `hidden_act` | **silu** | **situ（SiTU-GLU, beta=4/25）** | 激活实现不同 |
| `q_lora_rank` | null | **1536** | K3 MLA 多了 q LoRA |
| `mla_use_output_gate` | 无 | **true** | K3 MLA 多了输出门 |
| KDA `gate_lower_bound` / `use_full_rank_gate` | 无 | **-5.0 / true** | K3 KDA 门控不同 |
| `hidden_size` / `num_hidden_layers` | 2304 / 27 | 7168 / 93 | — |
| heads / experts | 32 heads / 256 experts / 8 激活 / 1 shared | 96 heads / 896 experts / 16 激活 / 2 shared | — |
| KDA:full 比例 | 20 : 7 (≈3:1) | 69 : 24 (≈2.9:1) | 基本一致 |
| 参数量/激活 | 48B / 3B | 2.8T / 104B | — |
| `routed_scaling_factor` | 2.446 | 1.0 | — |
| **量化** | **BF16（98GB，无 quant config）** | **MXFP4 W / MXFP8 A（QAT，~1.56TB）** | K3 的核心难点 KL 完全没有 |

### 结论

- **不能拿 KL 直接等价验证 K3**：AttnRes、Latent MoE、SiTU-GLU、MLA output gate、Vision、MXFP4 都不在 KL 里。
- **但 KL 是很好的“前半程”代理**：KDA + MLA + MoE 路由 + 混合层布局 + 1M 上下文 + 同词表都在，
  而且它是 **BF16、48B/3B、98GB**，8 卡 TYD 可容纳，能先把 KDA/MLA/MoE 的算子与图跑通，
  再叠加 K3 特有的模块。
