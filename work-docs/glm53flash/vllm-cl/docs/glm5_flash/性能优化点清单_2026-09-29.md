### P0-1 掐掉 KDA 状态 gather/scatter 的 host 路径（prefill 58%）

- **证据**：`vllm_cl/patch/patch_kda.py:330` / `:337`，34 层 prefill 合计 6.909 s；每次调用
  都做 `torch.any(indices<0)`、`torch.any(indices>=N)`、`indices.unique().numel()` 三个
  必然同步的检查，再加 `index_select`/`index_copy_`/`where`/`src.to(dtype)` 等若干小 op。
- **动作**：（a）把校验收进 `validate_data` 开关（默认关，debug 时才同步）；（b）非连续
  池视图下的 `index_copy_` 改按页 stride 寻址。
- **关联算子需求**：**#05 `dlc_kda_state_gather_scatter`**（完全新算子 → **2026-10-10 已交付并接入**，替代插件侧页表实现）。
- **覆盖判定（2026-10-10 更新）**：**本优化点已由 #05 融合算子完全覆盖**（2026-09-30 至 10-10 之间由插件侧「页表」Python 实现顶替）。
  算子同事给出的 `kda_state_pool_dlc.py` 已收编为 `vllm_cl/patch/kda_state_pool_dlc.py`，
  在**连续 `[P, page_len]` 页表**上做 `index_select` / 高级索引整行写回，页内再用 `narrow` 取递归窗口：

  | 几何 | gather native → 页表 | scatter native → 页表 |
  |---|---|---|
  | 打包页（stride(0)=135680，旧布局） | 2176 ms → 0.29 ms（**7500x**） | 11931 ms → 0.16 ms（**7.5 万 x**） |
  | 拆池后 dense（默认布局，P=1168,H=8,Dv=Dk=128 fp32） | 0.48/1.21 ms → 0.16/0.18 ms | 1.91/1.99 ms → 0.08/0.09 ms |

  （S=1/S=8，`warmup=2, iters=5`，dlc:0/1；同页表预建后差别在 0.05 ms 量级，故未做逐层缓存。）
  更重要的一点：新实现**不含任何 host 校验**，每次调用的 `torch.any`×2 + `unique()` 三次 D2H 同步
  一并消失（34 层 × 2 次 = 170 次/步）。
  开关：`DLC_KDA_STATE_POOL_OP=kernel|fast|native`（**默认 `kernel`**），`DLC_KDA_STATE_POOL_VALIDATE=1`
  可临时把越界/重复页校验加回来（会同步，勿在图里用）。回归测试 `tests/test_kda_state_pool.py`。
- **#05 融合算子（2026-10-10 已接入）**：真机 34 层 gather+scatter **0.76 ms/步**（S=1；页表实现 5.6 ms），
  单次 gather 0.022 ms / scatter 0.013 ms（需求上限 0.5/1.0 ms），无 host D2H、可 `DLCGraph` 捕获，
  比页表实现少 68 次 kernel 下发；`-1`（PAD_SLOT_ID）在 scatter 侧按契约跳过不写（模型路径不会传负值：
  prefill 用 `block_table[:, 0]`、cudagraph 填充尾用 `NULL_BLOCK_ID=0`）。
  验收：`op_requests/probes/probe_kda_state_gather_scatter_op.py`（dlc:0/1/2/3 全绿）与
  `op_requests/probes/probe_patch_kda_state_pool_dispatch.py`（三种模式 + 回退路径）。
  语义按 `op_requests/05_dlc_kda_state_gather_scatter.md` 执行。

> `_fused_operand`（decode 每步 306 次 view 物化）的完整归因、9 个操作数逐个定源与 A~F
> 落地办法见 [`_fused_operand_方案_2026-10-09.md`](_fused_operand_方案_2026-10-09.md)。
>
> **2026-10-10 更新**：方案 2（`MetadataPacker` 同 dtype 打包，每步 6 → 4 次 H2D）已落地，
> 见该文档 §3.2.2；方案 1（`compute_causal_conv1d_metadata` / `_build_chunk_metadata` 两段合一）
> 经复核**不按原写法实施**（exact-fit 规则会让拼接后的 view 每次多拷一份，且仅 prefill 有收益），
> 见 §3.1。

- **证据**：prefill 9,284 次 `aten::copy_`（self 9.27 s）、9,497 次 `aten::to`、5,896 次
  `_to_copy`、12,329 次 `custom_copy_stride_general`、9,419 次 `custom_reshape_offset`；
  decode 1,788 / 1,631 / 971 / 1,956 / 1,197。
  另有 `_thread.lock.acquire` 只有 4 次却占 7.86 s —— 异步 copy 线程被同步路径串行化。
- **动作**：逐模块归因（trace 已开 `--profiler-config.torch_profiler_with_stack=true`，
  可按 parent frame 归因到具体调用点），然后统一布局/对齐、去掉临时 `transpose/reshape/to`。

- **归因结果（2026-09-29，rank0 同一份 trace，按 `python_function` 栈帧 + 时间包含关系归因）**

  **机制**：DLC 的 `aten::copy` 只要源/目标 stride 不匹配、或需要跨 dtype 转换，就会落到
  `aten::copy_after_async` → `driver.memcpy` / `synMemCopyAsync` / `synMemCopySync` /
  `driver.DoAsyncJob` 这条 **host staging** 链路。`aten::copy_after_async` 是它在主线程的入口
  （prefill 7,934 次 / decode 1,438 次），driver 侧那几个只是同一次搬运的下半段，不能重复计。
  下面的表用「最内层仓库栈帧」把它归到发起方：

  prefill（step0 = 11.975 s）：

  | 发起方（最内层栈帧） | 调用 | `copy_after_async` | self 合计 | 单次 | 干什么 |
  |---|---|---|---|---|---|
  | `scatter_states_dlc` `patch_kda.py:337` | 34 | 136 | **5.829 s** | 171 ms | `index_copy_` 写回 stride(0)=135680 的池视图 |
  | `_convert_req_index_to_global_index_native` `sparse_mla.py:362` | 22 | 55 | **1.225 s** | 56 ms | 512-wide NoPE 稀疏 MLA 兜底；元凶是 `div(floor)` 与 2-D 高级索引（见根因 3） |

- **根因三类**
  1. **跨 stride 的分页池搬运**：状态池每页 512 KiB、页间有 4 KiB 空洞，`index_select`/`index_copy_`
     无法按 512 B 对齐做块 DMA，只能逐行 staging → scatter+gather 合计 6.8 s/步（prefill 的 57%）。
     → **#05 覆盖**。
  2. **逐 token 的 Python 参考实现**：`_run_kda`（prefill 兜底）和 `native_kpool_indexer_step`
     每个 token 十几次小 op（`transpose`/`expand`/`reshape_offset`/`foreach_*`/`.to()`），单次便宜、
     量级巨大 → **#03 / KPool 三件套（#07 扩展 / #09 扩展 / #19）覆盖**。
  3. **高频小索引算子落在 DLC 的慢路径上**：`_convert_req_index_to_global_index_native` 22 次调用吃掉
     1.225 s（prefill 的 10%）。真机逐 primitive 定位（每个 primitive 单独进程，`dlc:0`，`[20, 2048]`
     int32；脚本 `op_requests/probes/probe_int_index_host_staging.py`）后，元凶**不是** `.long()`：

     | op | ms/call | staged DMA/call |
     |---|---|---|
     | `torch.div(x, 64, rounding_mode="floor")` | 0.505 | **3** |
     | `x // 64`（floor_divide） | 0.075 | 0 |
     | 2-D 高级索引 `block_table[row, column]` | **2.971** | 0 |
     | `torch.gather(rows, 1, idx)` | 0.139 | 0 |
     | 摊平后 1-D `index_select` | 4.380 | 0 |
     | `x.long()`（int32→int64，gather 的 index 必须是 int64） | 0.168 | 1 |

     即：`div(..., rounding_mode="floor")` 每次调用产生 3 次 host 往返，2-D 高级索引单次 2.9 ms。
     换成 `//` + 「每个 token 取一整行 block table 后沿 dim1 `torch.gather`」后
     **4.04 ms / 11 次 staged → 0.56 ms / 1 次 staged（7.2x）**，结果逐位不变。
