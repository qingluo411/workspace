## 一、[Operator Request][P0] `dlc_kda_causal_conv_prefill`：GLM5 真实 prefill 长度（N>=3072）会卡死设备

### 问题摘要

`torch.dlc_kda_causal_conv_prefill` 在 GLM-5.3-Flash 的真实几何（D=3072、kernel=4、bf16、N=3072/4096）下
**会把设备卡死**：调用不返回、进程空转、该卡之后连 `a + 1.0` 都会挂住，必须复位设备才能再用。
根因已定位到 kernel —— 它把**整条序列**一次性搬进片上 VMEM，没有按 token 分块，host 侧也没有任何长度上限校验。

小 N（<=2560）时该算子数值完全正确（`out_err` bf16 量级、`state_err=0`），但**还有一个更隐蔽的 P0**：
`direct_state` 快路径忽略 state stride，在真实池子布局（conv 段后面跟着 SSM 段）下会读错行并把 conv state
写进 recurrent state 的内存 —— 见下面「另一个 P0」。

### 实测现象

### 根因与修复建议

**根因：整条序列一次性驻留 VMEM，没有 token 分块。**

```c
// DLC_Custom_Kernel/dlc_kernels/conv/kda_causal_conv_prefill.c:95-101
    int bf16_row_blocks = dim_bf16 / 32;
    tensor vmem_input  = (tensor)mem->vmem_addr;
    tensor vmem_weight = vmem_input + max_len * bf16_row_blocks;   // 按“最长序列”预留
    tensor vmem_output = vmem_weight + weight_blocks;
    tensor vmem_state  = vmem_output + max_len * bf16_row_blocks;  // 再按“最长序列”预留
```

- `max_len` 取整批最长序列；D=3072 时 bf16 每 token 占 6144 B，输入 + 输出 + state + weight 合计，
  约 2048~3072 token 就到顶；
- 片上 VMEM 只有 `kVmemSize = 0x1000000`（16 MB，`DLCSynapse/external_includes/Veloce_Architecture.h:40`），
  N=4096 直接越界写爆，kernel 再也回不来；
- host wrapper（`aten/src/ATen/native/dlc/CausalConv1d.cxx:430+`）没有任何 N 上限校验或分块处理。

**修复建议（按优先级）：**
1. **按 token 分块**：把 `vmem_input` / `vmem_output` 改成循环复用（每次处理固定 ≤1024 token 的块，
   块内保持现有滑窗逻辑），这样任意长度都不再受 VMEM 限制；
2. 如果短期不做分块，**至少在 host 侧加上限校验**（如 `TORCH_CHECK(n <= kMaxTokensPerLaunch, ...)`），
   让调用方拿到明确报错，而不是把设备打挂（挂死设备是**不可恢复**的，只能复位）。

### 另一个 P0：`direct_state` 路径忽略 state stride —— 真实池子上读错行、并写坏 SSM 段

`make_flat_storage_view` + `params` 的设计意图（见 `CausalConv1d.cxx:28-58` 的文件头注释）是
**零拷贝**：把整个共享池的 base 地址交给内核，再由内核按 stride 逐行取每块 conv 段的
`state_len × D` 个元素、跳过行间的 SSM 段 / 页填充。但当前 `kda_causal_conv_prefill.c`
只读了 `params[0]`(state_len) 和 `params[5]`(state_slots)，地址计算写死成
`state_addr + slot * state_len * dim_bf16 / 32`（`:128,178,181,185`）——
即**硬编码行距 = `state_len × padded_dim`**，`params[1..4]`（dim/tap/slot stride、storage_offset）完全没被使用。

GLM5 的 conv state 恰好就是「每块内 conv 段后面跟着 SSM 段」的布局：
`MambaBase.bind_kv_cache`（`vllm/model_executor/layers/mamba/abstract.py:29-45`）把
`[B,1,1,page_bytes]` 按 `pages[:, off:off+nbytes].view(dtype).view(-1,*shape)` 切成视图，
因此视图的 **stride(0) = `page_size_bytes / itemsize`**，而每块的 conv 段只有 `L*D` 个元素。
TP8 下本层 page ≈ 18,432 B(conv bf16) + 524,288 B(recurrent fp32) ⇒ stride(0) ≈ 271,360 个元素，
而 `L*D = 9,216`，相差约 29 倍。`kda.py:383-388` 再 `transpose(-1,-2)` 得到 `[S,D,L]`（`stride(1)==1`），
于是 host 的 `direct_state` 条件（`CausalConv1d.cxx:549-551`）**全部满足**，走的正是这条错误的快路径。

实测（`probes/probe_new_kda_conv_prefill_state_stride.py`，dlc:0 与 dlc:1 两台设备输出完全一致）：

```
dev=dlc:0 D=3072 L=3 GAP=2048 用例=[4, 4] idx=[1, 2]
[A 新算子 + 紧凑行距 L*D   ] out_err=9.766e-04  state_err=0.000e+00  行间段被改写元素数=0     (stride0=9216,  L*D=9216)
[B 新算子 + 池子行距 L*D+GAP] out_err=3.545e+00  state_err=3.453e+00  行间段被改写元素数=4096  (stride0=11264, L*D=9216)
[D 现有 _causal_conv1d + 紧凑行距] out_err=7.812e-03  state_err=0.000e+00  行间段被改写元素数=0     (stride0=9216,  L*D=9216)
[C 现有 _causal_conv1d + 池子行距] out_err=3.906e-03  state_err=0.000e+00  行间段被改写元素数=0     (stride0=11264, L*D=9216)
```

- **A 组**（此前所有测例的形态）通过；**B 组只把 state 行距从 `L*D` 改成 `L*D+2048`，数据内容完全相同，结果全错**。
- B 组的「行间段」在脚本里填了哨兵值 3.0（真实池子里这一段就是 recurrent/SSM 状态），
  跑完**有 4096 个哨兵元素被改写**（2 个活跃 slot × 2048，正好被写满）——
  即算子不只是算错，而是**直接写坏了相邻的 state 内存**。
- **C 组是关键对照**：同一份池子行距布局，现有 `torch._causal_conv1d` 完全正确
  （`out_err=3.9e-03`、`state_err=0`、哨兵零改写），因为它的 kernel 确实按
  `state_offset + c*st_dim + j*st_tok + row*st_seq` 寻址（`causal_conv1d.c:155-165`）。
  也就是说：**同样的分页 stride 契约，现有算子兑现了、新算子没有。**

修复建议（二选一，强烈建议前者）：
1. **内核按 `params` 的 stride 寻址**（这才是设计本意）：行基址用 `slot_stride`、tap 偏移用 `tap_stride`、
   通道偏移用 `dim_stride`，再叠加 `storage_offset`；现有 `_causal_conv1d` 的 kernel 就是这么算的
   （`DLC_Custom_Kernel/dlc_kernels/conv/causal_conv1d.c:155-165`：
   `state_offset + c * st_dim + j * st_tok + row * st_seq`），可直接参考；
2. 或者 host 侧把 `direct_state` 收紧为「`stride(0) == state_len * padded_dim`」才允许直通，
   其余走拷贝路径 —— 但拷贝是 27.8 MB × 2/层，prefill 每步 34 层 ≈ 1.9 GB，不可接受，只能作临时兜底。

### 附带项（非阻塞，建议一并处理）

1. **把 host 校验整体下沉到 `validate_data` 开关（默认关；debug 时才同步）**：
   `CausalConv1d.cxx:497-512` 现在**无条件**做 `qsl.to(at::kCPU)` + `indices.to(at::kCPU)`，
   再用 CPU 指针逐请求校验（`qsl` 单调性、页号范围、活跃槽位不重复）。GLM5 是 34 层 × 每次调用，
   等于每步 68 次强制 D2H，且必然无法被 CUDA graph 捕获。
   请照上游 `causal_conv1d_fn(..., validate_data=False)` 的既有约定
   （`vllm/model_executor/layers/mamba/ops/causal_conv1d.py:498,615`；
   插件内同名的 `patch_causal_conv1d.py` 实现也带这个开关）把这段放进 `validate_data` 分支，
   默认不做任何 host 侧同步。

2. **被跳过行的输出必须预置零**：校验默认关掉之后，`-1` / 越界这类「跳过」输入会直接进 kernel，
   而 kernel 对被跳过的行只 `continue`、不写输出（`kda_causal_conv_prefill.c:115`），
   输出缓冲又是 `at::empty`（`CausalConv1d.cxx:593`）→ **该行会漏脏值**。
   请把输出改成 `at::zeros` 预置（现有算子就是这么做的，`CausalConv1d.cxx:146`），
   或让 kernel 对被跳过行补写 0，使它的语义与 `slot == 0` 的 null 分支（写 0、state 不动）一致。

3. **关于 `-1`（PAD_SLOT_ID）的结论：不要求「放行 `-1`」这个动作本身，它现在不阻塞**。
   - **插件/GLM5 的模型路径不会产生负页号**：`non_spec_state_indices_tensor` 取自 block table 首列
     （`vllm/v1/attention/backends/gdn_attn.py:257,330`，1D、无负值），而 padding 行的填充值在两边都是
     `NULL_BLOCK_ID = 0`：DLC runner 显式 `blk_table_tensor[num_reqs:num_reqs_padded].fill_(NULL_BLOCK_ID)`
     （`vllm_cl/worker/dlc_model_runner.py:2229-2231`，注释 "Block 0 is reserved for padding"），
     GDN metadata builder 同理（`gdn_attn.py:487`）；真实请求块号 ≥ 1（0 号块是 null block，永不分配）。
     插件另外两处的行为也可以佐证不会传负值：update 路径对 `idx < 0` 直接抛 `IndexError`
     （`vllm_cl/patch/patch_kda.py:12-14` 的 `_page_index`），recurrent 路径只是留了防御性 `if idx < 0: continue`
     （`patch_kda.py:117`）。
   - **上游契约确实允许 `-1`**（`causal_conv1d_fn(..., pad_slot_id=-1)`，文档示例
     `cache_indices = [pad_slot_id, 1, 20, pad_slot_id]`，`ops/causal_conv1d.py:534-540`；
     `PAD_SLOT_ID = -1`，`vllm/v1/attention/backends/utils.py:45`），plugins 的 drop-in 实现也跳过它
     （`vllm_cl/patch/patch_kda.py:38`；上游参考实现 `patch_causal_conv1d.py:355-360` 还明确
     「`== pad_slot_id` → 输出 0 并跳过、`<0` 且非 pad → 报错」）。
   - 所以只要第 1+2 项落实（默认不校验 + 输出预置零），`-1` 与越界都会退化成「静默跳过 + 输出全 0」，
     与现有 `torch._causal_conv1d` 的 pad 行为一致，插件侧就不需要额外过滤分支。
     我们不会因为这条阻塞接入；唯一希望的是别出现「默认路径不校验、又不预置零」的组合。
   - 复现（安全，不会卡设备）：`probe_new_kda_conv_prefill.py dlc:0 9` 的第 9 例 `neg-slot`，
     当前会打印 `RuntimeError: dlc_kda_causal_conv_prefill: state index out of range at request 0`。
4. **可选：接受 2D `state_indices`（与 #02 对齐）**。现状 host 只收 1D `[B]`（`CausalConv1d.cxx:460-461`）。
   经核对，GLM5 prefill 上游本来就是 1D（`gdn_attn.py:257/330` 的 `block_table_tensor[:, 0]`，
   上游契约 `causal_conv1d.py:524-525` 写的是 `cache_indices: (batch)`），**所以这不是缺陷、无需修**；
   只是 #02（`dlc_kda_causal_conv_update`）接受 `[B,T]` 取第 0 列，两边形态不一致，若顺手对齐可减少接入时的分支。

### 关于 `weight` dtype 与输入布局的说明（**无需修改**）

- host 要求 `weight` 为 fp32 `[D,4]`（`CausalConv1d.cxx:443-445`）。GLM5 侧 `self._merged_conv_weight`
  **本来就是 fp32 `[D,4]`**（`vllm/models/glm5next/nvidia/kda.py:211-215` 用 `params_dtype=torch.float32`
  构建 q/k/v conv1d，`kda.py:396-405` 拼接为 `[3D,4]`），直接传即可。
  （此前草稿里"GLM5 是 bf16、需插件缓存 fp32 版本"的说法**已作废**，实测/源码核对后确认是 fp32。）
- `qkv` 需 `[N,D]` bf16 contiguous（上游传的是 `qkv_ns.transpose(0,1)`）；
  `conv_state` 需 `[S_slot,D,state_len]` bf16、通道维 stride==1（`[pages,tap,dim]` buffer 的 `permute(0,2,1)` 视图即可，
  wrapper 内部走 `make_flat_storage_view` 零拷贝，不满足时才回退拷贝）；
  `query_start_loc` int32 `[B+1]`、`has_initial_state` bool `[B]` —— GLM5 全部满足。

### 验收标准

5. **池子布局用例必须过**：`probe_new_kda_conv_prefill_state_stride.py` 的 B 组（行距 `L*D+2048`）

### 附：复现脚本全文（`probes/probe_new_kda_conv_prefill.py`）

```python
"""#01 新算子 dlc_kda_causal_conv_prefill 实测（2026-09-22）。

输入形状按 GLM5 模型：D=3072=(64*128*3)/TP8, kernel=4, state=[S_slot,D,3]（SD 布局的 transpose 视图）。
reference：向量化的 fp32 depthwise causal conv + silu（等价于 patch_kda._native_conv_sequence）。
kernel 约定（kda_causal_conv_prefill.c）：state 行序 旧->新；取「最后 3 行」为 history；
slot 0 = null（输出全 0、state 不写）；处理完把「最新 state_len 个原始投影」写回 state。

用法：`python probe_new_kda_conv_prefill.py <dev> [case_ids]`，例如
`python ... dlc:0 3,4,5,6,7,8,9` 只跑第 3~9 例（跳过已知会卡死设备的 N>=3072 长序列用例），
便于「一例一张干净卡」地逐例验证（每个用例内部都已 `dlc.synchronize()`）。
"""
import sys
import time
import torch

dev = sys.argv[1] if len(sys.argv) > 1 else "dlc:0"
ONLY = set(sys.argv[2].split(",")) if len(sys.argv) > 2 else None


def want(tag):
    # 默认**不跑**第 2 例（N=4096）：它会把设备卡死；要跑必须显式写 case id（如 `... dlc:0 2`）。
    if ONLY is not None:
        return tag in ONLY
    return tag != "2"

torch.manual_seed(0)
W, HIST = 4, 3


def ref_vec(x_dl, w_dl, hist_dl):
    """x_dl:[D,N] bf16, w_dl:[D,4] fp32, hist_dl:[D,3] bf16 -> ([D,N], [D,3])"""
    N = x_dl.shape[1]
    xs = torch.cat([hist_dl.float(), x_dl.float()], 1)          # [D, 3+N]
```

```python
"""#01 第二个 P0 的最小复现：`dlc_kda_causal_conv_prefill` 的 `direct_state` 快路径忽略 state stride。

背景
----
真实运行时 conv_state 不是独立连续缓冲，而是 Mamba 分页池里的一个视图：
  MambaBase.bind_kv_cache -> pages[:, off:off+nbytes].view(dtype).view(-1, *shape)
所以每个 slot 的行距 = page_size_bytes / itemsize（TP8 下 ≈ 271,360 元素），
而 conv 段本身只有 L*D = 9,216 元素；中间那一段是 recurrent/SSM 状态（绝不能被写）。

host 的 `direct_state` 条件（CausalConv1d.cxx:549-551：stride(1)==1、stride(0)/(2) 为偶数、
storage_offset 偶数、padded_dim==dim）在真实池子上**全部满足**，于是走了「零拷贝直通」；
但 kernel 只读了 params[0](state_len) 与 params[5](state_slots)，地址写死成
`slot * state_len * dim_bf16 / 32`（kda_causal_conv_prefill.c:128,178,181,185），
params[1..4] 的 stride/storage_offset 完全没用 —— 于是读错行、并写进行间的 SSM 段。

本脚本用「数据完全相同、只有 state 行距不同」的四组对照复现：
  A) 新算子 + 紧凑行距 L*D            —— 期望通过（这也是此前所有测例的形态）
  B) 新算子 + 池子行距 L*D+2048       —— 期望失败；并用哨兵值证明行间段被改写
  C) 现有 torch._causal_conv1d + 池子行距 —— 同一布局下现有算子的表现（对照）
  D) 现有 torch._causal_conv1d + 紧凑行距 —— C 的基线

B 组里那 2048 个「行间」元素在脚本里填了哨兵值 3.0；若跑完哨兵被改，就证明算子写坏了
真实池子里的 recurrent 段，而不只是数值错。

用法：python probe_new_kda_conv_prefill_state_stride.py [dlc:N]    （安全，不会卡设备）
"""
import sys
import torch

dev = sys.argv[1] if len(sys.argv) > 1 else "dlc:0"
torch.manual_seed(0)
W, HIST, D = 4, 3, 3072
L = HIST                      # conv_state 宽度（num_spec=0 时 = kernel-1）
GAP = 2048                    # 模拟「行间的 recurrent/SSM 段 + 页填充」
SENTINEL = 3.0
lens = [4, 4]
idxs = [1, 2]


def ref_rows(rows, x_dn, w2d):
    """rows: list(L) of [D]；x_dn: [D,n] -> (out [D,n] bf16, new rows list(L))"""
    rows = [r.clone() for r in rows]
    outs = []
    for t in range(x_dn.shape[1]):
        win = rows[-3:]
        y = sum(w2d[:, k] * win[k] for k in range(3)) + x_dn[:, t] * w2d[:, 3]
        outs.append(torch.nn.functional.silu(y).to(torch.bfloat16))
        rows.append(x_dn[:, t])
        rows = rows[-L:]
    return torch.stack(outs, 1), rows


def build(strided):
    """返回 (state_view, gap_slice_fn, base_rows)"""
    slots, page = 3, (L * D + GAP if strided else L * D)
    pool = torch.full((slots, page), SENTINEL, dtype=torch.bfloat16, device=dev)
    for s in range(slots):
        pool[s, : L * D] = torch.randn(L * D, dtype=torch.bfloat16, device=dev) * 0.4
    if strided:
        state = pool.as_strided((slots, D, L), (page, 1, D), 0)
        rows = {s: [pool[s, t * D:(t + 1) * D].clone() for t in range(L)] for s in idxs}
    else:
        state = pool.view(slots, L, D).transpose(1, 2)     # [S,D,L]，行距 = L*D
        rows = {s: [state[s][:, t].clone() for t in range(L)] for s in idxs}
    return pool, state, rows, page


def check(tag, state, pool, page, rows, out, ref_out, ref_new):
    oerr = (out.float() - ref_out.float()).abs().max().item()
    serr = max(max((a.float() - b.float()).abs().max().item()
                   for a, b in zip([state[s][:, t] for t in range(L)], ref_new[s]))
               for s in idxs)
    sent = 0
    if page != L * D:                       # 行间段是否被改写
        for s in range(pool.shape[0]):
            sent += int((pool[s, L * D:] != SENTINEL).sum().item())
    print(f"[{tag}] out_err={oerr:.3e}  state_err={serr:.3e}  "
          f"行间段被改写元素数={sent}  (stride0={state.stride(0)}, L*D={L * D})", flush=True)
    return oerr, serr, sent


def main():
    N = sum(lens)
    x = (torch.randn(N, D, dtype=torch.bfloat16, device=dev) * 0.5).contiguous()
    w2d = (torch.randn(D, W, dtype=torch.float32, device=dev) * 0.3).contiguous()
    qsl = torch.tensor([0, lens[0], N], dtype=torch.int32, device=dev)
    sidx = torch.tensor(idxs, dtype=torch.int32, device=dev)
    hinit = torch.tensor([True, True], dtype=torch.bool, device=dev)
    print(f"dev={dev} D={D} L={L} GAP={GAP} 用例={lens} idx={idxs}", flush=True)

    for tag, strided in (("A 新算子 + 紧凑行距 L*D   ", False),
                         ("B 新算子 + 池子行距 L*D+GAP", True)):
        pool, state, rows, page = build(strided)
        ref_out = torch.empty(N, D, dtype=torch.bfloat16, device=dev)
        ref_new = {}
        for b, s in enumerate(idxs):
            st, en = int(qsl[b]), int(qsl[b + 1])
            o, nr = ref_rows(rows[s], x[st:en].transpose(0, 1).contiguous(), w2d)
            ref_out[st:en] = o.transpose(0, 1)
            ref_new[s] = nr
        out = torch.dlc_kda_causal_conv_prefill(x, w2d, state, qsl, sidx, hinit,
                                                activation="silu", null_state_id=0)
        torch.dlc.synchronize()
        check(tag, state, pool, page, rows, out, ref_out, ref_new)

    # C/D：现有算子在同样两种布局下的表现（它内部会先 x.transpose(0,1).contiguous()）
    for tag, strided in (("D 现有 _causal_conv1d + 紧凑行距", False),
                         ("C 现有 _causal_conv1d + 池子行距", True)):
        pool, state, rows, page = build(strided)
        ref_out = torch.empty(N, D, dtype=torch.bfloat16, device=dev)
        ref_new = {}
        for b, s in enumerate(idxs):
            st, en = int(qsl[b]), int(qsl[b + 1])
            o, nr = ref_rows(rows[s], x[st:en].transpose(0, 1).contiguous(), w2d)
            ref_out[st:en] = o.transpose(0, 1)
            ref_new[s] = nr
        try:
            out_cf = torch._causal_conv1d(
                x.transpose(0, 1), w2d.to(torch.bfloat16),
                torch.zeros(D, dtype=torch.bfloat16, device=dev), state, qsl, sidx, hinit)
            out = out_cf.transpose(0, 1).contiguous()
            torch.dlc.synchronize()
            check(tag, state, pool, page, rows, out, ref_out, ref_new)
        except Exception as e:                                   # noqa: BLE001
            print(f"[{tag}] 调用失败: {type(e).__name__}: {str(e)[:160]}", flush=True)


main()
```

## 二、[Operator Request][P0] `dlc_kda_causal_conv_update`：kernel 每次整池 DMA（真机几何慢 ≈13x）+ host 端 D2H 同步 + pad 行输出脏值

> 本节内容较多（含背景、全部实测与 5 个脚本）。**只想快速看「问题 / 修法 / 复现」请看精简版
> [`给算子组_02_update_issue.md`](给算子组_02_update_issue.md)**（一页，含一条命令跑完 4 个问题的脚本）。

### 问题摘要

`torch.dlc_kda_causal_conv_update` 的**数值是逐元素正确的**（plain decode 全部 `state_err=0`；spec/多 token 用例见「实测现象」，本阶段不要求），
但每次调用都会搬一遍**整个 conv state 池**，成本与「池子字节数」成正比、**与活跃请求数无关**：

- 真机几何（`num_blocks=1509`、D=3072、池子 26.5 MB）**单次 7.4 ms vs 现有 `torch._causal_conv1d_update` 0.59 ms（≈13x）**；
- **耗时随槽位总数线性增长**（4 -> 3072 槽位：0.61 -> 14.73 ms），B=8 只用 8 个页也照样慢；
- 34 层 KDA 每 token 各调一次 ⇒ 单步 decode 多花约 250 ms/token。

**成本归因（2026-09-22 晚重测，修正了早期结论）**：13x 里的 **94% 在 kernel 内部**，不是 host wrapper：

| 构成 | 实测（S=1509, D=3072） | 占比 |
|---|---|---|
| **kernel 内整池 `HBM2VMem`（`kda_causal_conv_update.c:109`）** | **≈ 6.9 ms** | **≈ 94%** |
| host wrapper 的 4 遍整池拷贝（`:401/:402/:414/:415`） | 0.47 ms | ≈ 6% |

早期版本把原因写成「host wrapper 整池拷贝 4 遍 HBM 往返」，那是**按流量推算的估计，不是实测**，方向错了：
真机 HBM 带宽很高（26.5 MB 连续拷贝 ≈ 0.06 ms），host 的 4 遍只有 0.47 ms；真正的 O(槽位数) 成本在 kernel 里。

另外还有 2 个必须一并处理的问题：host 侧 `qsl.to(at::kCPU)` 造成**每次调用强制 D2H 同步**（不传 `num_accepted_tokens` 时还有第二次，
plain decode 走的就是这条）、`idx=-1`（pad slot）行的 `out` 是 `at::empty` 的**脏值**。

**范围（2026-09-22 明确）**：适配初期只要求 **plain decode** —— 每请求 1 个 token、`state_len=3`、
不传 `num_accepted_tokens`。**MTP/spec（多 token、`num_accepted_tokens` 提交语义、`state_len>3`）本阶段不做**，
本次不要求算子组处理（精简版见 [`给算子组_02_update_issue.md`](给算子组_02_update_issue.md)）。

### 实测现象

1. 数值（D=3072，2026-09-22 实测，`probe_new_kda_conv_update.py` / `..._window.py`）：

| 用例 | 新算子 | 现有 `_causal_conv1d_update` |
|---|---|---|
| plain decode B=4，含 null slot 0 | `out_err=0`、`state_err=0`；null 行输出全 0、state 不变 | 一致（null 行输出全 0、state 不变） |
| spec T=4 `accepted=[0,2,4,1]`、T=6 `[3,0]` | `out_err=0`、`state_err=0` | **不吻合**：`out_err=1.07`、`state_err=2.85` |
| L=4 / L=6（num_spec=1/3），含 `accepted=0` | 全部 `state_err=0`（`out_err<=9.8e-04`） | 全部不吻合（`state_err≈2.6~3.0`） |
| D=320（非 256 倍数） | 报错 `V1 BF16 kernel requires D_conv to be a multiple of 256` | 支持 |

> 下表里 spec / L>3 的行仅作背景参考：**本阶段只验收 plain decode**。

2. 性能（D=3072；**每档先 warm-up 一次再计时**，排除首次 kernel 加载的一次性开销，`..._scaling.py`）：

| 槽位数 | 新算子（plain B=8 单 token） | 现有 `_causal_conv1d_update` | 新算子（spec T=4, acc=3） |
|---|---|---|---|
| 4（退化：idx 会重复） | 0.61 ms | 0.86 ms | 0.34 ms |
| 256 | 1.75 ms | 0.61 ms | — |
| 1024 | 5.17 ms | 0.57 ms | 5.26 ms |
| **1509（真机 `num_blocks`）** | **7.49 ms** | **0.59 ms（≈13x）** | **7.41 ms** |
| 2048 | 9.99 ms | 0.60 ms | — |
| 3072 | 14.73 ms | 0.72 ms | — |

**关键特征：新算子耗时随「槽位总数」线性增长，而现有算子与槽位规模无关** —— 成本来自对整个池子的无条件搬运。

3. **成本归因（`probe_new_kda_conv_update_cost.py`，dlc:6，2026-09-22 晚）**：

```
=== A) host 侧各步开销（S=1509, L=3, D=3072，池子 26.5 MB）===
  连续->连续 copy_（基线）      = 0.06 ms
  transpose(1,2).contiguous()   = 0.07 ms
  上一行 + clone()              = 0.12 ms
  wrapper 的 4 遍（①~④）        = 0.47 ms

=== B) 活跃请求数 B 的影响（slots=1509, D=3072）===
  slots=1509 B=  1 | 池= 26.53 MB | out_err=0.000e+00 |  7.59 ms
  slots=1509 B=  8 | 池= 26.53 MB | out_err=0.000e+00 |  7.45 ms
  slots=1509 B= 64 | 池= 26.53 MB | out_err=9.766e-04 |  7.50 ms     <-- 与活跃请求数无关

=== C) 每槽位字节数的影响（slots=1509, B=8）===
  slots=1509 D=  256 | 池=  2.21 MB |  1.29 ms | 0.584 ms/MB
  slots=1509 D=  768 | 池=  6.63 MB |  2.29 ms | 0.346 ms/MB
  slots=1509 D= 1536 | 池= 13.26 MB |  4.02 ms | 0.303 ms/MB
  slots=1509 D= 3072 | 池= 26.53 MB |  7.39 ms | 0.279 ms/MB
  线性拟合：t ≈ 0.74 ms + 0.251 ms/MB（≈ 4082 MB/s 的整池搬运带宽）

=== D) 汇总 ===
  算子整体调用           = 7.37 ms
  其中 host 4 遍整池拷贝 = 0.47 ms（6.3%）
  => kernel 内整池 DMA + 计算 ≈ 6.91 ms
```

即：**成本 ∝ 池子字节数（固定 ~0.7 ms 启动开销 + ~0.25 ms/MB），与活跃请求数无关**，
等价于每次调用都按 ~4 GB/s 把整池读一遍 —— 与 `:109` 的整池 `HBM2VMem` 完全对应。

4. 大槽位健壮性（`probe_new_kda_conv_update_cost.py` 可外推，另测）：slots=8192（池子 144 MB）**不卡死、结果仍正确，
   但单次 347 ms** —— 成本继续随槽位增长，说明这是无条件整池扫描，不是容量故障。

5. `idx=-1`（pad slot）行：输出不是 0，而是未初始化内存的脏值（实测 `out_maxabs≈1.05~1.71`）；
   对应 state 未被写（这一点是对的）。

6. **update 算子没有 #01 那个 state stride 缺陷**（`probe_new_kda_conv_update_stride.py`）：
   紧凑行距与池子行距（行间 2048 个哨兵）两组都是 `out_err=0 / state_err=0 / committed_err=0 / 行间段被改写=0`。
   原因是 host 在 `:401` 无条件 `conv_state.transpose(1,2).contiguous()` 把池子拉平后才交给 kernel，
   kernel 内部 `slot * state_len * dim_bf16` 的紧凑寻址因此成立 —— 代价就是那 0.47 ms 的整池拷贝。
   因此若按第 2 条改零拷贝 strided，必须同时让 kernel 支持行距元数据，否则会重演 #01 的 P0。

7. host 单步开销明细（同一脚本）：`transpose(1,2).contiguous() = 0.07 ms`、`+clone() = 0.12 ms`、
   `at::empty(26.5 MB) = 0.02 ms`。

8. 设备侧备注（非算子问题，供参考）：`dlc:0` 上 strided->连续 的整池拷贝异常慢
   （26.5 MB ≈ 2.98 ms，dlc:1~7 均 ≈ 0.04~0.07 ms，复位后依旧）；**但 8 张卡上算子本体耗时一致（7.3~7.6 ms）**，
   所以上面所有归因结论不受该异常影响。后续建议单独核查卡 0 的 strided 拷贝路径。

### 根因与修复建议

**1) [P0] kernel 每次调用无条件把整个池搬进 VMEM** —— `kda_causal_conv_update.c:109`：

```c
/* vmem_commit = all slot snapshots */
HBM2VMem(hbm_conv_state, vmem_commit, state_slots * state_len * dim_bf16);
```

1509 槽位 = 26.5 MB 的整池 DMA，每次调用都做，而实际需要它的只有：

- 卷积计算：只读**活跃** slot 的行（`:131` `HBM2VMem(hbm_conv_state + slot*state_len*dim_bf16/32, ...)`）；
- 回写：只写**活跃** slot（`:235-237` `Vmem2HBM(vmem_commit + slot*..., hbm_committed_state + slot*..., ...)`）；
- 整池预载的唯一作用，是让「本次没有提交快照的 slot」在写回时保留原值（`accepted<=0` 的分支）。

但第二个返回值 `committed_state`（`[state_len,D,state_slots]` 全池快照）**调用方根本不用**：
上游 `vllm/models/glm5next/nvidia/kda.py:445` 只取 `out`，插件侧同样只取 `out`。

建议修复（按顺序）：
1. 删掉 `:109` 的整池预载；把 `accepted <= 0` 的活跃 slot 在 `:235` 直接跳过回写
   （该 slot 的 state 本来就不该变），语义完全不变；
2. 更好的做法：第二个输出只覆盖**活跃 slot**（或做成可选输出 / 直接去掉），并在 ABI 注释里写明；
3. host 侧 `committed_state` 的 `at::empty`（每次新分配 26.5 MB）一并去掉。

**2) [P1] host wrapper 的 4 遍整池拷贝**（不是 13x 的主因，但仍应做掉）：

```cpp
// aten/src/ATen/native/dlc/CausalConv1d.cxx:401-415
auto wc = weight.transpose(0, 1).contiguous();
auto conv_state_t = conv_state.transpose(1, 2).contiguous();   // ① 整池拷贝
auto committed_state_t = conv_state_t.clone();                 // ② 再整池拷贝一次
// ... k.launch("custom_kda_causal_conv_update");
auto committed_state = committed_state_t.transpose(1, 2).contiguous();  // ③ 又一遍整池拷贝
conv_state.copy_(committed_state);                             // ④ 再整池写回
```

实测 0.47 ms/次（34 层 ≈ 16 ms/token）。建议走 `make_flat_storage_view`（`CausalConv1d.cxx:60`）零拷贝 strided 访问，
**但前提是 kernel 支持行距元数据**（现在 `:131`/`:236` 硬编码 `slot*state_len*dim_bf16`）；
否则零拷贝会把 #01 的「忽略 state stride」缺陷复制到 update 上（见上面实测现象第 6 条）。

**3) [P0] 每次调用强制 D2H 同步（阻断 graph 捕获）**：

```cpp
// CausalConv1d.cxx:345-350  无条件：只为做 monotonic / max_query_len 的 host 校验
TORCH_CHECK(qsl[-1].item<int>() == qkv_flat.size(0), ...);   // :346  D2H
auto qsl_cpu_check = qsl.to(at::kCPU);                       // :349  D2H（并等设备队列排空）
// CausalConv1d.cxx:376-378  num_accepted_tokens=None 分支：再同步一次
auto qsl_cpu = qsl.to(at::kCPU);
auto acc_cpu = accepted.to(at::kCPU);
for (int64_t b = 0; b < B; ++b) aptr[b] = qptr[b + 1] - qptr[b];
accepted.copy_(acc_cpu);                                     // 再由 host 拷回设备
```

- 插件侧 KDA decode 路径是走 graph 的（`vllm_cl/worker/dlc_model_runner.py:5110` 用
  `vllm_cl.compilation.dlc_graph.CUDAGraphWrapper` 包住模型，`vllm_cl/platform.py:261` 注册为该后端默认）；
  wrapper 里的 host 段代码只在**捕获时**跑一次，`accepted.copy_(acc_cpu)` 会被捕获成一条**固定源**的 H2D，
  replay 时沿用捕获时算出的长度 —— 语义上就是 stale；`qsl.to(at::kCPU)` 的校验同样只在捕获时算一次。
- 建议：host 校验放到 `validate_data` 开关下（默认关，debug 时才同步）；`None` 分支改成设备侧张量运算
  （`accepted = qsl[1:] - qsl[:-1]`）或直接在 kernel 里按 `qsl` 推长度；`qsl[-1]` 的检查同样进开关。

**4) [P1] pad 行输出脏值**：kernel 对 `slot<0` / `slot>=state_slots` 是 `continue`（不写 out），
而 host 用 `at::empty` 申请输出，所以脏值会漏给调用方（实测 `out_maxabs≈1.05~1.71`）。
建议与现有算子一致，用 `at::zeros` 预置（现有 wrapper 就是 `at::zeros`，`CausalConv1d.cxx:242`），
或在 kernel/host 里把被跳过行显式写 0。

**5) [后续，本次不要求] spec 提交语义（启用 MTP 时再对齐）**：
- 新算子与「**整窗滚动 L 行 + 处理完 `num_accepted_tokens` 个 token 后提交快照**」的参考实现**逐元素一致**
  （我们的参考按 flash-linear-attention 语义写，L=3/4/6、`accepted=0` 都对齐，`state_err=0`）；
- 旧 kernel 注释写的是另一套：`offset = na<0 ? 0 : na-1`、`shift = na<0 ? seqlen : 1`
  （`DLC_Custom_Kernel/dlc_kernels/conv/causal_conv1d_update.c:37-40,148-149,198`），即把 `num_accepted_tokens`
  当作**读窗口偏移 + 整窗回写**，因此 `accepted < T` 时与窗口参考对不上（`state_err≈2.6~3.0`）。
- 两套语义不能互换。**适配初期不走 MTP/spec，所以这次不需要算子组处理**；后续启用 MTP 时再确认以哪套为契约
  （本条仅作背景留档）。

**其他接口约束（接入要用，供确认）**：
- `qkv` 2D `[N,D]` 时必须显式传 `query_start_loc`（现有算子可省），且 `max_query_len >= 每请求长度`；
- `D` 必须是 256 的倍数（GLM5 D=3072 满足）；
- 活跃请求的 state slot 必须互不重复（否则结果未定义）；
- `conv_state` 为 `[S_slot,D,state_len]` bf16、`state_len>=3`（GLM5 是 3+num_spec）。

### 附：复现脚本全文（`probes/probe_new_kda_conv_update.py`）

```python
"""#02 新算子 dlc_kda_causal_conv_update 实测（2026-09-22）。

对比：A) fp32 reference（向量化） B) 新算子 C) 已有 torch._causal_conv1d_update
kernel 约定（kda_causal_conv_update.c）：
  y[t]=SiLU(s[-3]*w0+s[-2]*w1+s[-1]*w2+x[t]*w3)；state 行序 旧->新，新值追加到末行；
  只在处理完 num_accepted_tokens 个 token 后提交快照；slot 0 = null（输出 0、state 不动）；
  slot<0 或越界 -> 既不写输出也不写 state（输出缓冲未初始化）。
"""
import time
import torch

import sys

dev = sys.argv[1] if len(sys.argv) > 1 else "dlc:0"
torch.manual_seed(0)
W, HIST = 4, 3


def ref_update(base, slot, xs, w2d, accepted):
    """base:[S,L,D]; xs:[T,D] -> ([T,D] bf16, snap[L,D] bf16)

    2026-09-22 晚修正：初版只滚动最后 HIST 行、把前 L-HIST 行原样留在快照里，L>3 时与算子
    （以及 `probe_new_kda_conv_update_window.py` 的参考）不一致，误报 L=6 失败。正确语义是
    **整窗滚动 L 行**，滑窗读最后 3 行，第 accepted 个 token 后整窗快照。
    """
    L = base.shape[1]
    h = base[slot].float().clone()
    outs, snap = [], base[slot].clone()
    for t in range(xs.shape[0]):
        y = torch.nn.functional.silu(
            h[L - 3] * w2d[:, 0] + h[L - 2] * w2d[:, 1] + h[L - 1] * w2d[:, 2]
            + xs[t].float() * w2d[:, 3])
        outs.append(y.to(torch.bfloat16))
        h = torch.cat([h[1:], xs[t].float()[None]], 0)
        if t == accepted - 1:
            snap = h.to(torch.bfloat16)
    return torch.stack(outs) if outs else xs.new_empty((0, xs.shape[1])), snap


def case(name, D, lens, slots=4, idxs=None, acc=None, state_len=HIST, qkv3d=False):
    B, N = len(lens), sum(lens)
    idxs = idxs if idxs is not None else list(range(1, B + 1))
    xs = (torch.randn(N, D, dtype=torch.bfloat16, device=dev) * 0.5).contiguous()
    w2d = (torch.randn(D, W, dtype=torch.float32, device=dev) * 0.3).contiguous()
    base = torch.randn(slots, state_len, D, dtype=torch.bfloat16, device=dev) * 0.5
    qsl = torch.tensor([0] + torch.cumsum(torch.tensor(lens), 0).tolist(),
                       dtype=torch.int32, device=dev)
    sidx = torch.tensor(idxs, dtype=torch.int32, device=dev)
    acc_t = None if acc is None else torch.tensor(acc, dtype=torch.int32, device=dev)

    ref_out = torch.empty(N, D, dtype=torch.bfloat16, device=dev)
    ref_buf = base.clone()
    for b in range(B):
        s, e = int(qsl[b]), int(qsl[b + 1])
        a = (e - s) if acc is None else acc[b]
        if e <= s:
            continue
        o, snap = ref_update(base, idxs[b], xs[s:e], w2d, a)
        ref_out[s:e] = o
        if idxs[b] > 0:
            ref_buf[idxs[b]] = snap

    buf = base.clone()
    t = time.time()
    out, committed = torch.dlc_kda_causal_conv_update(
        xs, w2d, buf.transpose(-1, -2), sidx,
        query_start_loc=qsl, num_accepted_tokens=acc_t,
        max_query_len=max(lens), activation="silu", null_state_id=0)
    torch.dlc.synchronize()
    dt = time.time() - t
    rows = torch.cat([torch.arange(int(qsl[i]), int(qsl[i + 1])) for i in range(B)
                      if idxs[i] > 0]) if any(i > 0 for i in idxs) else torch.zeros(0, dtype=torch.long)
    oerr = (out[rows].float() - ref_out[rows].float()).abs().max().item() if rows.numel() else 0.0
    serr = (buf.float() - ref_buf.float()).abs().max().item()
    cerr = (committed.transpose(-1, -2).float() - ref_buf.float()).abs().max().item()
    print(f"[{name}] D={D} lens={lens} idx={idxs} acc={acc} L={state_len}", flush=True)
    print(f"    out_err={oerr:.3e} state_err={serr:.3e} committed_err={cerr:.3e} t={dt:.4f}s",
          flush=True)
    if 0 in idxs:
        r = idxs.index(0)
        seg = out[int(qsl[r]):int(qsl[r + 1])]
        print(f"    null slot: out_all_zero={bool((seg == 0).all())} "
              f"state_unchanged={bool(torch.equal(buf[0], base[0]))}", flush=True)
    if -1 in idxs:
        r = idxs.index(-1)
        seg = out[int(qsl[r]):int(qsl[r + 1])]
        print(f"    idx=-1: out_all_zero={bool((seg == 0).all())} "
              f"out_maxabs={seg.abs().max().item():.3e} "
              f"state_unchanged={bool(torch.equal(buf[-1], base[-1]))}", flush=True)
    return out, buf


print("=== 1) plain decode: B=4 单 token, null slot 0 ===", flush=True)
case("decode-b4", 3072, [1, 1, 1, 1], idxs=[1, 2, 0, 3])
print("=== 2) spec decode: T=4, accepted=[0,2,4,1] ===", flush=True)
case("spec-T4", 3072, [4, 4, 4, 4], idxs=[1, 2, 3, 1], acc=[0, 2, 4, 1])
print("=== 3) spec: T=6, 部分接受 ===", flush=True)
case("spec-T6", 3072, [6, 6], idxs=[1, 2], acc=[3, 0])

case("3d-b2", 3072, [2, 2], idxs=[1, 2], acc=[1, 2], qkv3d=True)
print("=== 5) idx=-1（pad slot）===", flush=True)
case("neg-idx", 3072, [1, 1], idxs=[-1, 2])
print("=== 6) D=320（非 256 倍数）===", flush=True)
try:

except Exception as e:

print("=== 8) 与已有 torch._causal_conv1d_update 对比（plain decode B=4）===", flush=True)

    max_query_len=1, activation="silu", null_state_id=0)
torch.dlc.synchronize()

real = torch.tensor([0, 1, 3], device=dev)
print(f"    real row: old vs new out_err={(o_old.float()-o_new.float())[real].abs().max().item():.3e}"
      f"  state_err={(b_old.float()-b_new.float())[[1,2,3]].abs().max().item():.3e}", flush=True)
for nm, o, b in (("old", o_old, b_old), ("new", o_new, b_new)):
    print(f"    {nm}: null-row0 out_all_zero={bool((o[2] == 0).all())}"
          f"  state[0]_unchanged={bool(torch.equal(b[0], base0[0]))}", flush=True)
```

### 附：state 宽度 / spec 语义复现脚本全文（`probes/probe_new_kda_conv_update_window.py`）

```python
"""#02 state 宽度（num_spec）与 spec 语义复核（2026-09-22）。

GLM5 的 conv state 宽度 L = kernel-1+num_spec。真机 num_blocks=1509、L=3+num_spec。
参考实现：state 是「整窗」滑动的 L 行缓冲，滑窗读最后 3 行，新 token 追加到末行；
         num_accepted_tokens 之后提交快照。
本脚本：L=3/4/6 下对比 新算子 dlc_kda_causal_conv_update 与 已有 _causal_conv1d_update。
"""
import sys
import torch

dev = sys.argv[1] if len(sys.argv) > 1 else "dlc:4"
torch.manual_seed(0)
W = 4
D = 3072


def ref_one(slot_state, xs, w2d, accepted):
    """slot_state:[L,D] 旧->新；xs:[T,D] -> ([T,D], snap[L,D])"""
    h = slot_state.float().clone()
    L = h.shape[0]

    outs = []
    for t in range(xs.shape[0]):
        y = torch.nn.functional.silu(
            h[L - 3] * w2d[:, 0] + h[L - 2] * w2d[:, 1] + h[L - 1] * w2d[:, 2]
            + xs[t].float() * w2d[:, 3])
        outs.append(y.to(torch.bfloat16))
        h = torch.cat([h[1:], xs[t].float()[None]], 0)
        if t == accepted - 1:
            snap = h.clone()
    return (torch.stack(outs) if outs else xs.new_empty((0, D)), snap.to(slot_state.dtype))
```

```python
"""#02 槽位规模扫描：新 update 算子 vs 已有 _causal_conv1d_update（2026-09-22）。

def ref_one(base_slot, xs, w2d, accepted):
```

```python
"""#02 `dlc_kda_causal_conv_update` 耗时归因探针（2026-09-22 晚）。

背景：早期结论认为「慢 13x」来自 host wrapper 的整池拷贝。本脚本把成本拆开实测：

  A) host 侧各步的实际开销（连续拷贝基线 / transpose+contiguous / +clone / wrapper 的 4 遍）；
  B) 固定槽位数与 D，只改「活跃请求数 B」——若耗时几乎不变，说明成本与活跃请求无关；
  C) 固定槽位数与 B，只改「每槽位字节数 D」——区分「按字节」还是「按槽位固定开销」；
  D) 汇总：host 各步之和 vs 算子整体调用。

结论（见 给算子组_01_02_修复要点.md 第二节）：成本 90% 以上来自 kernel 内部
`kda_causal_conv_update.c:109` 的整池 HBM2VMem（约 4 GB/s 量级、与活跃请求数无关），
host wrapper 的 4 遍整池拷贝在真机几何下只有约 0.27 ms。

用法：
    python -u probe_new_kda_conv_update_cost.py [dlc:N]     # 默认 dlc:0
安全：不会卡设备；仍建议一例一张干净卡。
"""
import sys
import time
import torch

dev = sys.argv[1] if len(sys.argv) > 1 else "dlc:0"
W, L = 4, 3


def bench(fn, n=8):
    """每次调用后同步，取 n 次最小值（排除异步记账与抖动）。"""
    fn()
    torch.dlc.synchronize()
    best = float("inf")
    for _ in range(n):
        t = time.time()
        fn()
        torch.dlc.synchronize()
        best = min(best, time.time() - t)
    return best * 1e3


def ref_out(x_d, slot_state_ld, w2d):
    """单请求、单 token：y = silu(h[-3]*w0 + h[-2]*w1 + h[-1]*w2 + x*w3)，h 为 [L,D] 旧->新。

    注意入参都必须是 1D（x_d:[D]），返回 [D]；不要传 [1,D]，否则 stack 后会多一维、
    与 out 广播成 [B,B,D]，err 变成假值。
    """
    y = (slot_state_ld[L - 3].float() * w2d[:, 0]
         + slot_state_ld[L - 2].float() * w2d[:, 1]
         + slot_state_ld[L - 1].float() * w2d[:, 2]
         + x_d.float() * w2d[:, 3])
    return torch.nn.functional.silu(y).to(torch.bfloat16)


def case(slots, B, D, n=8):
    torch.manual_seed(0)
    x = (torch.randn(B, D, dtype=torch.bfloat16, device=dev) * 0.5).contiguous()
    w2d = (torch.randn(D, W, dtype=torch.float32, device=dev) * 0.3).contiguous()
    pool = torch.randn(slots, L, D, dtype=torch.bfloat16, device=dev) * 0.5
    view = pool.transpose(-1, -2)                      # [S,D,L] stride=(L*D,1,D)，非连续
    qsl = torch.arange(0, B + 1, dtype=torch.int32, device=dev)
    idx = (torch.arange(B, dtype=torch.int32, device=dev) % (slots - 1)) + 1

    want = torch.stack([ref_out(x[b], pool[idx[b]], w2d) for b in range(B)])
    out, _ = torch.dlc_kda_causal_conv_update(
        x, w2d, view, idx, query_start_loc=qsl, max_query_len=1,
        activation="silu", null_state_id=0)
    err = (out.float() - want.float()).abs().max().item()
    t = bench(lambda: torch.dlc_kda_causal_conv_update(
        x, w2d, view, idx, query_start_loc=qsl, max_query_len=1,
        activation="silu", null_state_id=0), n=n)
    pool_mb = slots * L * D * 2 / 1024 / 1024
    return t, err, pool_mb

    pool = torch.randn(S, Lc, D, dtype=torch.bfloat16, device=dev)

    def four_passes():
        t = pool.transpose(1, 2).contiguous()          # ①
        c = t.clone()                                  # ②
        pool.copy_(c.transpose(1, 2).contiguous())     # ③+④

    return {
        "连续->连续 copy_（基线）": bench(lambda: dst.copy_(flat)),
        "transpose(1,2).contiguous()": bench(lambda: pool.transpose(1, 2).contiguous()),
        "上一行 + clone()": bench(lambda: pool.transpose(1, 2).contiguous().clone()),
        "wrapper 的 4 遍（①~④）": bench(four_passes),
    }


print(f"dev={dev}  K=4, state_len={L}", flush=True)

print("\n=== A) host 侧各步开销（真机几何 S=1509, L=3, D=3072，池子 26.5 MB）===", flush=True)

for k, v in host.items():
    print(f"  {k:26s} = {v:7.2f} ms", flush=True)

for B in (1, 8, 64):

curve = []

(mb0, t0), (mb1, t1) = curve[0], curve[-1]
slope, intercept = (t1 - t0) / (mb1 - mb0), t0 - (t1 - t0) / (mb1 - mb0) * mb0
print(f"  线性拟合：t ≈ {intercept:.2f} ms + {slope:.3f} ms/MB"

t_full, _, _ = case(1509, 8, 3072)
print(f"\n=== D) 汇总（slots=1509, B=8, D=3072）===", flush=True)

print(f"  其中 host 4 遍整池拷贝              = {host['wrapper 的 4 遍（①~④）']:7.2f} ms"
```

### 附：池子行距正确性脚本全文（`probes/probe_new_kda_conv_update_stride.py`）

```python
"""#02 `dlc_kda_causal_conv_update` 在分页池子布局（真实 GLM5 形态）下的正确性 + 开销对照。

问题背景：prefill 算子（`dlc_kda_causal_conv_prefill`）走 `direct_state` 快路径时会忽略
state 行距（见 `probe_new_kda_conv_prefill_state_stride.py`）。update 算子是否也有同样问题？

本脚本用同一份数据、两种 state 视图各跑一次：

  A) 紧凑 [S,L,D] `transpose(1,2)` -> [S,D,L]，行距 = L*D；
  B) 池子 [S,page] `as_strided` -> [S,D,L]，行距 = L*D+GAP（模拟 conv 段后面跟着 SSM 段的真实页），
     行间 GAP 段预填哨兵 3.0。

对 out / 就地 state / 行间哨兵各做断言，并与 fp32 逐窗递推 reference 对比。

实测结论（2026-09-22 晚，dlc:1/dlc:6）：**update 算子没有 prefill 那个 stride 缺陷** ——
A、B 两组都是 `out_err=0 / state_err=0 / 行间段被改写=0`。原因是 host wrapper 在
`CausalConv1d.cxx:401` 无条件做了 `conv_state.transpose(1,2).contiguous()`，
把池子视图拉平成紧凑布局后才交给 kernel（kernel 内部 `slot*state_len*dim_bf16` 的紧凑寻址因此成立）。
代价是每次调用多一遍整池拷贝（真机几何约 0.07 ms/层，34 层约 2.4 ms/token）。

用法：
    python -u probe_new_kda_conv_update_stride.py [dlc:N]     # 默认 dlc:0
安全：不会卡设备。
"""
import sys
import time
import torch

dev = sys.argv[1] if len(sys.argv) > 1 else "dlc:0"
torch.manual_seed(0)
W, L, D = 4, 3, 3072
GAP, SENT = 2048, 3.0
B = 2
idxs = [1, 2]


def ref(base_LD, x_TD, w2d):
    """逐窗递推：h:[L,D] 旧->新；返回 (out[T,D] bf16, 末态 snap[L,D] bf16)。"""
    h = base_LD.float().clone()
    outs = []
    for t in range(x_TD.shape[0]):
        y = (h[0] * w2d[:, 0] + h[1] * w2d[:, 1] + h[2] * w2d[:, 2]
             + x_TD[t].float() * w2d[:, 3])
        outs.append(torch.nn.functional.silu(y).to(torch.bfloat16))
        h = torch.cat([h[1:], x_TD[t].float()[None]], 0)
    return torch.stack(outs), h.to(torch.bfloat16)


x = (torch.randn(B, D, dtype=torch.bfloat16, device=dev) * 0.5).contiguous()
w2d = (torch.randn(D, W, dtype=torch.float32, device=dev) * 0.3).contiguous()
qsl = torch.arange(B + 1, dtype=torch.int32, device=dev)
sidx = torch.tensor(idxs, dtype=torch.int32, device=dev)

print(f"dev={dev} D={D} L={L} GAP={GAP}  (state 视图不同、数据相同)", flush=True)
for tag, strided in (("A 紧凑行距 L*D   ", False), ("B 池子行距 L*D+GAP", True)):
    slots, page = 3, (L * D + GAP if strided else L * D)
    pool = torch.full((slots, page), SENT, dtype=torch.bfloat16, device=dev)
    for s in range(slots):
        pool[s, : L * D] = torch.randn(L * D, dtype=torch.bfloat16, device=dev) * 0.4
    if strided:
        state = pool.as_strided((slots, D, L), (page, 1, D), 0)
        rows = {s: pool[s, : L * D].view(L, D).clone() for s in idxs}
    else:
        state = pool.view(slots, L, D).transpose(1, 2)
        rows = {s: state[s].transpose(0, 1).contiguous().clone() for s in idxs}

    ref_out = torch.empty(B, D, dtype=torch.bfloat16, device=dev)
    ref_snap = {}
    for b, s in enumerate(idxs):
        o, snap = ref(rows[s], x[b:b + 1], w2d)
        ref_out[b] = o[0]
        ref_snap[s] = snap

    t = time.time()
    out, committed = torch.dlc_kda_causal_conv_update(
        x, w2d, state, sidx, query_start_loc=qsl, max_query_len=1,
        activation="silu", null_state_id=0)
    torch.dlc.synchronize()
    dt = time.time() - t

    oerr = (out.float() - ref_out.float()).abs().max().item()
    serr = 0.0
    for s in idxs:
        got = state[s].transpose(0, 1).contiguous().float()
        serr = max(serr, (got - ref_snap[s].float()).abs().max().item())
    sent = 0
    if strided:
        for s in range(slots):
            sent = max(sent, int((pool[s, L * D:] != SENT).sum().item()))
    # committed_state 是 [S,D,L] 全池快照：只对本次活跃 slot 与 reference 比（其余 slot 不在本次语义内）
    cerr = 0.0
    for s in idxs:
        got = committed[s].transpose(0, 1).contiguous().float()
        cerr = max(cerr, (got - ref_snap[s].float()).abs().max().item())
    print(f"[{tag}] out_err={oerr:.3e} state_err={serr:.3e} committed_err={cerr:.3e} "
          f"行间段被改写={sent} t={dt * 1e3:.2f}ms", flush=True)
```
