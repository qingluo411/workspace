# GLM-5.3-Flash 算子需求「已有算子覆盖」核查结论

本文件回答一个问题：`op_requests/` 里 18 条融合算子需求，是否已经有 DLC 算子能覆盖？
结论先行（2026-09-22 晚最终定稿）：**18 条中 6 条可由现有算子覆盖（撤回），
1 条应改写为「扩展已有算子」，5 条应改写为「修复算子功能或精度」，6 条是全新算子**；
即实际需要提给算子组的是 **12 条**。（历次修正：
#02 的 page 0 是 vLLM 保留的 null block，kernel 跳过属设计行为，由「需修复」移入「撤回」；
#18 的页几何经复核全部 512B 对齐，由「需扩展」移入「撤回」；
#16 复核后由「需扩展」改为「新增独立算子」；
**算子组交付 5 个 KDA 专用新算子后实测：#06 移入「撤回」，#03/#04 移入「需修复」**；
**最终决定（2026-09-22 晚）：#01~#04 四个新算子全部采用、由算子组修复，
#01/#02 也由「撤回」移入「需修复」，合计 12 条**，
明细见本文件末尾新增的「2026-09-22 新算子实测」一节，修复单见 `给算子组_01_02_修复要点.md` /
`给算子组_03_04_修复要点.md`。）

## 详细结论与实测记录

### A. 已被完整覆盖（建议撤回）

**#12 `dlc_vllm_concat_and_cache_mla_`（576 与 512 NoPE 均可用）**

```
[kpe=64  576-layout bs=256] OK  latent_err=0.000e+00 kpe_err=0.000e+00
[kpe=0   512-NoPE   bs=256] OK  latent_err=0.000e+00 kpe_err=0.000e+00
```

- 参数要求（源码 `FusedOps.cpp: dlc_vllm_concat_and_cache_mla_impl`）：`slot_mapping` 必须 **int64**、
  `kv_cache` 必须 contiguous、`block_size` 为 2 的幂、bf16 下 `kvc_dim` 为 256 的倍数；`kpe_dim < 256`
  即允许 0。
- 插件现状（`vllm_cl/attention/sparse_mla.py:60`）因 `k_pe.shape[-1] == 0` 判断走了 native，实际可直接调用。

**#14 `dlc_mhc_post`**

```
mhc_post out_err=3.901e-03 out_dtype=torch.bfloat16
```

- 语义与 native 一致：`out = post_mix * x + comb_mixᵀ @ residual`。
- 注意：`comb_res_mix` 需要 **flat** `[..., hc_mult*hc_mult]`（与 `dlc_mhc_pre` 返回的 `cm` 直接对接），
  `x` 为 `[..., hidden_size]`（单路），不是 `[..., hc_mult, hidden_size]`。

**#01 `_causal_conv1d`（KDA 短卷积 prefill）**

> **2026-09-22 晚更新（最终决定）**：下面「建议撤回新增需求」的结论**已被取代** —— 适配组改为采用算子组新交付的
> `dlc_kda_causal_conv_prefill`（修复 N 分块卡死等问题后接入）；本节关于 `_causal_conv1d` 的布局约束仍然成立，
> 作为修复期间的**兜底方案**。见文末「2026-09-22 新算子实测」与
> [`给算子组_01_02_修复要点.md`](给算子组_01_02_修复要点.md)。

```
[prefill] out_err=1.953e-03  state_err=0.000e+00
```

- 布局约束（踩过的坑，接入时必须满足）：
  - `x` 需 `[dim, T]` 且 channel 维连续（channel-last）；
  - `weight` 需 **2D** `[dim, K]`（KDA 的 `[dim,1,K]` 需 squeeze）；
  - `conv_states` 需 **通道维 `stride==1`**，即 `[pages, tap, dim]` 视图（由 `[pages, tap, dim]` buffer `permute(0,2,1)` 得到）；否则报 `conv state dim axis must be contiguous`；
  - bf16 下 `storage_offset` 必须为偶数；
  - APC 相关参数（`block_idx_first_scheduled_token` / `block_idx_last_scheduled_token` /
    `initial_state_idx` / `num_computed_tokens`）目前必须为 `None`。

```
index_select+where (gather w/ mask): OK | index_copy_ (scatter): OK
[#17] out dtype: torch.float32 shape (128, 8192) err: 0.0006024837493890548
```

**#02 `_causal_conv1d_update`（KDA 短卷积 decode / spec 更新；2026-09-22 修正版）**

```
conv_state_indices=[0]      -> [0] skipped out_zero=True state_unchanged=True
conv_state_indices=[1]      -> [1] out_err=0.00e+00 state_err=0.00e+00
conv_state_indices=[2]      -> [2] out_err=0.00e+00 state_err=0.00e+00
conv_state_indices=[3]      -> [3] out_err=0.00e+00 state_err=0.00e+00
conv_state_indices=[0, 2]   -> [0] skipped ...; [2] out_err=0.00e+00 state_err=0.00e+00
conv_state_indices=[1, 0]   -> [1] out_err=0.00e+00 state_err=0.00e+00; [0] skipped ...
conv_state_indices=[-1]     -> [-1] skipped out_zero=True
conv_state_indices=[-1, 1]  -> [-1] skipped out_zero=True; [1] out_err=0.00e+00 state_err=0.00e+00
```

- 2026-09-21 的初版探针把 page 0 当作普通页（reference 用了它的历史），因此误报「`conv_state_indices==0`
  输出错误（0.86~1.16）」。
- 真实语义：kernel 硬编码 `null_block_id = 0` / `pad_slot_id = -1` 并跳过这两行
  （`causal_conv1d_update.c:65-66,145,293,346`），输出由 wrapper 预置零（`CausalConv1d.cxx:242`）。
  这与上游约定一致：`NULL_BLOCK_ID = 0`（`vllm/v1/attention/backends/utils.py:46`）、null block 永不分配
  （`vllm/v1/core/block_pool.py:188-191`）、CUDA graph padding 行显式填 `NULL_BLOCK_ID`
  （`short_conv_attn.py:467`）。**不是缺陷，而是必须保留的语义。**
- 结论：KDA decode / MTP verify 已完全覆盖，撤回新增需求；插件把 `patch_kda.py:45` 切到该算子即可，
  `conv_state_indices` 继续沿用 block table 首列。
- **2026-09-22 晚更新（最终决定）**：上面「撤回新增需求」的结论**已被取代** —— 适配组改为采用算子组新交付的
  `dlc_kda_causal_conv_update`（数值逐元素正确），由算子组修 kernel 内整池 DMA（`:109`，13× 的 94%）/ host 侧 D2H 同步 / pad 行脏值后接入；
  本节的 `_causal_conv1d_update` 事实仍然成立，作为修复期间的**兜底方案**。见
  [`给算子组_01_02_修复要点.md`](给算子组_01_02_修复要点.md) 第二节。
- 空槽约定差异（备查、无实际影响）：prefill kernel（`causal_conv1d.c:63,156,279,371`）只跳过 `-1`、
  不跳过 0，与 update kernel 不同；但 prefill 的索引同样来自 block table 首列（`short_conv_attn.py:371/183`，
  真实请求 ≥ 1），且 padded 行先被 `seqlen <= 0` 跳过，因此 vLLM 路径不会把 page 0 交给 prefill kernel，
  无需算子组改动。
- 探针：`probes/probe_causal_conv1d_state_index_zero.py`（2026-09-22 修正版）。


- 卡死时的 kernel dump（用户侧记录）显示 `custom_sparse_attention_kv_cache_bf16_h4`，参数
  `shape=[512,4,2,1,1]`（512 = head_dim）、`shape=[512,256,...]`（kv_cache）、`shape=[2048,2]`（topk），
  scalar `0.0441942 / 512 / 0 / 1`——即 rope 宽度为 0 的 512 布局。
- 源码 `FusedOps.cpp: dlc_sparse_attention_kv_cache`：head 数分派只覆盖 `2/4/8/64`，topk 只覆盖
  `256/512/1024/1536/2048`；GLM5 的 indexer 是 64 head（TP8→8）可用，但 topk 宽度 2051（2048 池 +
  3 个 tail token）超出现有分派。
- 结论：该需求应保留，但性质是「修复 512 NoPE 路径 + 扩展 topk 宽度」，而不是新增独立算子。

### C. 已被覆盖但能力不足，需要扩展（#03、#04、#13）

**#03 / #04 KDA delta-rule 核心已存在，缺逐通道 gate**

DLC 的 `chunk_gated_delta_rule` / `fused_recurrent_gated_delta_rule` 是 **GDN 形态**（per-head 标量 gate），
实测数值正确：

```
[chunk per-token g (natural) vs per-token ref] out_err=1.020e-04 state_err=8.773e-04
[recurrent per-head (T,H)] OK out_err=7.768e-04 state_err=1.878e-03
```

而 GLM5 KDA 的 gate 是 **逐通道**（`g1` 形状 `[1,T,H,D]`，D=head_dim=128，乘在 state 的 K 维上，
见 FLA `fused_recurrent_kda_fwd` 的 `p_gk = g + (bos*HV + i_hv)*K + o_k`）；逐通道输入被拒：

```
[chunk 3D per-channel] FAILED: g must be either flattened or batched, but got dim 4
[chunk 3D per-channel] FAILED: g batch size must be 1 when cu_seqlens is used, but got 32
[recurrent per-channel] FAILED: g batch size must be 1 when cu_seqlens is used, but got ...
```

第二个缺口是 gate 的**形成**：GLM5 用 bounded safe gate
`gate = lower_bound * sigmoid(exp(A_log) * (raw_g + g_bias))`（`kda_gate_cumsum_fwd_kernel`），
而 DLC 现有 `fused_gdn_gating` 与 `dlc_vllm_recurrent_gated_delta_rule_packed_decode` 用的是标准 GDN
`g = -exp(A_log) * softplus(a + dt_bias)`。chunk 路径还需要 chunk 内累计衰减（并乘 `RCP_LN2`）。

因此 #03/#04 的正确形态是：**扩展 `chunk_gated_delta_rule` / `fused_recurrent_gated_delta_rule`
支持逐通道 gate，并把 bounded safe gate + chunk 内累计衰减一并融合**，而不是另起一套 delta-rule。

**#13 `dlc_mhc_pre`**：核心已覆盖，只缺子层 RMSNorm。

```
mhc_pre  post_err=3.028e-05 cm_err=1.056e-04 layer_input_err=3.922e-03 | dtypes: fp32 fp32 bf16
```

- 源码 `aten/src/ATen/native/dlc/mhc_pre.cxx` 已把 Sinkhorn 迭代放进 kernel；
- 但签名没有 `norm_weight` / `norm_eps`（上游 `MHCPreOp` 有，并在 `layer_input` 上做 RMSNorm），
  插件目前只能在外层用 `forward_oot` 补一次 RMSNorm（多一次读写往返）；
- 返回形状也不同：kernel 返回 `cm` 为 flat `[num_tokens, hc_mult*hc_mult]`，接入方需自行 reshape。

**#16 SwiGLU + clamp**（2026-09-22 二次复核后归入「新增算子」，详见 D 节）：DLC 只有
`silu_and_mul` / `silu_and_mul_with_padding`，没有 `silu_and_mul_with_clamp`（`hasattr` 探测为 MISSING）。
GLM5 的 dense/shared/视觉 FFN 需要 `gate=clamp(x[:d], max=10)`、`up=clamp(x[d:], ±10)` 后
`silu(gate)*up`；routed expert 侧已由 `dlc_vllm_fused_moe_*` 的 `swiglu_limit` 覆盖。
复核结论：**不动共享的 `silu_and_mul`，新增独立算子 `dlc_silu_and_mul_with_clamp`**（与上游同名同语义）。

### C2. 原判「需扩展」、2026-09-22 复核后转为「可复用」（#18）

**#18 KV cache 清零**：已有 `dlc_vllm_zero_block_ids_`，复核结论是**本模型下直接可用**。

- kernel 源码 `DLC_Custom_Kernel/dlc_kernels/vllm/zero_block_ids.cpp`：
  `hbm_sizewords = ALIGN128(page_size_el)`、block 步长 `= ALIGN128(page_size_el)/32`（128B 单位）；
  即要求「**每块字节数必须是 512 B 的整数倍**」且 `page_size_el = 每块字节数/4`，
  否则写入长度与 block 步长会被 `ALIGN128` 放大、清错块并越过张量尾部。
- GLM-5.3-Flash 页几何（真机 spec：TP8、`--block-size 256`、`index_kpool=4`、`kv_lora_rank=512`、
  `mla_use_nope=true`）全部满足：

  | 页类 | 每块字节 | ÷512 | `page_size_el`(int32) |
  |---|---|---|---|
  | MLA full（256 token × 512 latent） | 262,144 | 512 | 65,536 |
  | KPool pool（`[64,128]`，行宽补齐到 256） | 32,768 | 64 | 8,192 |
  | KPool tail（`[2,4,128]`，补齐到 256） | 4,096 | 8 | 1,024 |
  | KDA conv state（`[3,3072]` bf16） | 18,432 | 36 | 4,608 |
  | KDA recurrent state（`[8,128,128]` fp32） | 524,288 | 1024 | 131,072 |

  （pool / tail 即使按未补齐的逻辑行宽算（16,384 B / 2,048 B）也同为 512B 整数倍，结论不依赖行宽补齐取值；
   `_entries` 是每个页类各一个张量入口，共 67 个，所以传的 `page_size_el` 是上表逐行的值。）
- 实测（`probes/probe_zero_block_ids_glm5_geometry.py`，2026-09-22）：按上表 5 类页各建 3 个 segment、
  每段 8 块、清 `{1,3,6}` → **5 类全部 `exact_match=True`**（输出 `ALL_ALIGNED_AND_EXACT: True`），
  命中块为 0 且相邻块逐元素未变。
- 09-21 初版探针里 `exact_match=False` 的用例，是把 bf16 页折算成 `page_el(int32)=64`（= 256 B/块）构造的
  「非 512B 对齐页」**人为反例**，GLM5 真实页不会出现：

```
[official-config int32]    nb=8  page_el(int32)=128 ids=[0,2,5] -> exact_match=True
[bf16 256B 页（人为反例）]  nb=8  page_el(int32)=64  ids=[1,3]   -> exact_match=False（实际清了 1,3,5,7）
[GLM5 真实 5 类页]          见上表                                -> exact_match=True
```

- 新增实测约束：同一次调用内**不能混用不同页大小的 segment**（kernel 只有一个 `page_size_el`），
  否则跨度大的那组会清错相邻分配；插件必须按「每块字节数」分组调用、同组 segment 等长且连续。
- 其余要求：`seg_addrs` 必须 int64 一维地址表（DLC 无 uint64 storage），**不支持 CPU fallback**。
- 结论：撤回「新增算子 / 需扩展」两种提法，改为**插件接入**（按页字节分组 + 512B 对齐自检）；
  若将来出现非 512B 整数倍的页，再请算子组支持按字节寻址（本模型已确认不会出现）。
