### 3.3 批大小为什么只有 2.3：边界是「host 一时没有 kernel 可下发」

`DLCSynapse/synapse_core/synapse_core.cpp:2385-2453`（`backEndPush`，唯一的异步提交线程）
把主线程放进 `g_kernelParmsQueue` 的 kernel 逐个搬进 `KernelQueue`，然后判断是否 flush：

| # | 条件 | 源码 | 实际占比 |
|---|---|---|---|
| 1 | 切 stream 或 device | `:2400`（`s != queue.k_stream`） | 极少（本插件单 stream） |
| 2 | **`getCurrentTaskCount() == 0`** 且队列非空 | `:2435` | **绝大多数** |
| 3 | `queue.full()`（`xys*_index >= curr_max_size`，`:1986` 每次 flush 后被重置为 `min_queue_size`） | `:2451` | 次之 |
| 4 | 监控线程超时 | `DLC_SYN_BATCHTIMEOUT_US`，默认 `LAUNCH_TIMEOUT_DURATION_US = 200000`（200 ms，`external_includes/dlc/utils.hpp:316`） | 不可能触发（一次批 ~150 µs） |

参数：`kMinQueueSize = 1`、`kMaxKernelNum = 1024`（`external_includes/kernel_info.hpp:32/45`）、
`max_queue_size = max(1, min(DLC_SYN_BATCHSIZE=1M, 1024)) = 1024`、
自适应 `EXPAND_FACTOR` 默认 2.0、`SHRINK_STEP` 默认 -1（`dlc/utils.hpp:768/785`）。

结论：**条件 2 决定了批的边界**——只要提交线程发现「主线程此刻没有更多 kernel 要下发」，
就把已经攒到的 kernel 立刻推下去；而 `curr_max_size` 每次 flush 后都被重置为 1，
自适应只在 1↔2↔4 之间摆动，从来攒不到 `kMaxKernelNum=1024`。
换句话说，**平均 2.3 个/批正是「host-bound」的签名**：设备消费（~150 µs/批）比 host 生产快，
每一个 python 空档都会切断一个批。这与 M5「设备空洞 389.5 ms/步、均值 98 µs」互为印证，
也说明批大小会随 D1（图捕获/预录）自然变大。

### 3.4 `reshape_offset*` / `convert_element_type*` 到底从哪来

这两族**不是模型里的算子**，而是 runtime 在实现 `aten::copy_` / `aten::to` / GEMM / 逐元素算子时，
对「非连续 / 非 512B 对齐」的操作数做布局归一化、对 dtype 不一致的输入做类型搬移的**内部子 kernel**。

**`reshape_offset`：decode 单步 818 个 top-level op 的子树里含它**（按最外层 python 帧归因）：

| python 帧 | 次数 | 说明 |
|---|---:|---|
| `vllm_cl/patch/patch_kda.py:480 _fused_operand` | 204 | **34 个 KDA 层 × 6 次调用**（`:568` `cu_seqlens`、`:581` `q/k/v`、`:582` `g/beta`），操作数全是 view，被强制 `contiguous()/clone()` |
| `vllm_cl/patch/patch_linear.py:33 _patched_apply` | 102 | linear 的输入/权重做 col-major 归一化 |
| `vllm_cl/patch/patch_mhc.py:112 _mhc_post` | 90 | 45 层 × 2 |
| `vllm_cl/patch/patch_block_table.py:117 _call` | 72 | kpool tail slot mapping |
| `vllm_cl/patch/models/kpool_indexer.py:724 _kpool_plans_without_host_reads` | 66 | kpool 计划 |
| `vllm/v1/attention/backends/utils.py:1131 mamba_get_block_table_tensor` | 34 | attention metadata |
| `patch_kda.py:197 _update_new_op` / `:503 _recurrent_decode_new_op` / `:726 forward` | 34 / 34 / 34 | KDA |

挂它的 top-level op：`aten::copy` 315、`custom_copy_stride_general` 151、`custom_matmul_t_pingpong_col_major` 102、

**小结**：两族合计 1366 条/步（34.8%），根因是
① 插件侧仍以 view 形式把 `q/k/v/raw_g/beta`、`block_table`、`state_indices` 交给融合算子（A6 的 `#04` ABI 扩展 + C3 就是治这个）；
