# 元数据 host→device 拷贝：归因与合并方案（2026-10-09）

> 范围：GLM-5.3-Flash DLC 路径上，**每步在 CPU 侧准备、再搬上设备**的 metadata
> （`query_start_loc`、`seq_lens`、block table、chunk indices、`input_ids`、logits indices…）。
> 不含：权重加载期拷贝、KV/state cache 初始化期拷贝、算子内部的 device 侧 staging。
> 相关：`性能优化点清单_2026-09-29.md`（P0-3 / P2-2）、`kpool_mla_dataflow.md`、
> `patch_mla_indexer.py` 里 GLM-5 跳过 indexer prefill 分块 metadata 的早退分支。

## 0. 结论（TL;DR）

- DLC 上一次 H2D 的**固定成本约 44 µs，与 payload 无关**（实测见 §1.2）。所以「元数据 H2D 太多」是
  **粒度**问题，不是体积问题；合并成一次拷贝就能把它压到噪声级。
- **已落地 1 处（2026-10-10 收尾）**：`patch_mla_indexer.py` 里为上游 Triton indexer 准备、
  GLM-5 根本不消费的 prefill 分块 metadata（5 个张量/chunk）**无条件跳过**，回退开关
  `DLC_KPOOL_INDEXER_PREFILL_CHUNKS` 已删除。
- ✅ **已落地（2026-10-10）**：`CpuGpuBuffer.copy_to_gpu` 那批按 §3.2 落地——同 dtype 的段打包进
  一条常驻 pinned/device buffer，每步 H2D 由 6 次降到 4 次（`vllm_cl/worker/metadata_packer.py`，见 §3.2.2）。
- ⛔ **复核后不做**：`compute_causal_conv1d_metadata` / `_build_chunk_metadata` 的「两段合一」按原写法
  会被 launcher 的 exact-fit 规则反噬（拼接后的 view 每次多拷一份），且仅在 prefill 有收益，见 §3.1。
- **剩下的固定开销属 runtime**（P2-2：`synHostMalloc` / `driver.memcpy` / `backendPush` 随每次下发），
  插件/算子侧无法消除，只能由 runtime 侧优化。

## 1. 机制与实测

### 1.1 为什么小数组也贵

DLC 的 `aten::copy` 只要源在 host，就走 host staging：`aten::copy_after_async` →
`synHostMalloc` / `driver.memcpy` / `synMemCopyAsync` / `backendPush`。这条链路上每次下发都有固定成本
（P2-2 已记录），与数据量无关；vLLM V1 又天然是「CPU 侧持有 metadata、每步上传」的设计，
于是同样几个 KB 的数据被拆成几十~几百次拷贝，固定成本被放大几十倍。

### 1.2 实测（dlc:0，空闲卡，2026-10-09）

| 场景 | 耗时 |
|---|---|
| 900 × `64×int32` H2D（逐个 `.to(dev, non_blocking=True)`，pinned 源） | **39.9 ms** |
| 900 × `dst[i].copy_(src, non_blocking=True)`（目标预分配） | 39.9 ms |
| 1 × `57600×int32`（同样数据合并成一次） | **0.10 ms** |
| 单次平均 | ≈ 44 µs |

- 同样数据、同样 pinned 源，**逐个拷比合并拷慢约 400×**。
- `pin_memory` 在 DLC 上可用：`DLCPlatform.is_pin_memory_available() == True`、`tensor.is_pinned() == True`。
  即这批拷贝已经是 pinned + `non_blocking=True`，慢的不是「没 pin」，而是**下发次数**。

### 1.3 数量级（2026-09-29 trace，rank0）

| 场景 | 总量 | 其中 metadata 上传 | 上限估算 |
|---|---|---|---|
| prefill（step0 = 11.975 s） | `copy_after_async` 7,934 次 | ≈ **180 次/步**（`async_tensor_h2d` 68 + `compute_causal_conv1d_metadata` 68 + `copy_to_gpu` 44） | ≈ 8 ms/步 |
| decode（step1 = 1.749 s） | `copy_after_async` 1,438 次 | 余额 ≈ 446 次中一部分（未逐个定位） | ≤ 20 ms/步（≈1%） |

decode 已归因的头部是 `_fused_operand` 306、`native_kpool_indexer_step` 231、`_forward_native_nope` 231、
`patch_kda.py:528` 136、`_metadata` 88（已删），都不是 metadata H2D。

> ⚠️ 口径提醒：prefill 归因表里还有一行「其余零散 ≈900 次（11%）」，那 900 次是
> `fused_moe` router 84、`patch_kda.py:528` 136、`glm5_indexer` 88 等**混合**来源，metadata 只占约 180 次。
> 口语里说过的「39.9 ms/步」是把 900 次全当成 metadata 的**合成压测上限**，不是 trace 实测归属，
> 两个数不要混用。精确归因请按 §4 重采一次带栈帧的 trace。

## 3. 合并方案

### 3.0 已落地：跳过 GLM-5 不消费的 indexer prefill 分块 metadata

- 代码：`vllm_cl/patch/patch_mla_indexer.py` 的 `_patched_build_prefill_chunk_metadata` 在
  `_glm5_kpool_build_active` 为真时直接返回 `None`；该标志由 `_use_glm5_native_compressed_slot_mapping`
  在 GLM-5 构建期间置位/复位（`build_prefill_chunk_metadata` 没有 builder 参数，只能这样区分调用方）。
- 依据：`prefill.chunks` 的唯一消费者是上游 `SparseAttnIndexer`
  （`vllm_cl/ops/sparse_attn_indexer.py:281-346`），而 DLC GLM-5 的 indexer 是 `DLCGlm5NextIndexer`
  （`patch_glm5next.py:209` → `glm5_indexer.py:276`），只读
  `query_start_loc` / `raw_seq_lens` / `block_table_tensor` / `slot_mapping`；
  上游 `Glm5NextMLAAttention` 已被重绑（`patch_glm5next.py:292`），`SparseAttnIndexerKpool` 不会构造。
- 兼容（2026-10-10 更新）：**回退开关已删除**，GLM-5 构建期一律跳过；其他模型不经过这条分支，行为不变。
  判定收在 `_should_skip_glm5_prefill_chunks()`（仅为测试保留接缝，生产只看 `_glm5_kpool_build_active`）。
- 测试：`tests/test_kpool_metadata_native.py`
  `test_glm5_indexer_prefill_chunks_are_skipped_by_default`（含端到端 `meta.prefill.chunks == []`）、
  `test_glm5_build_scope_marks_prefill_chunk_skip`。

### 3.1 方案 1：attention metadata 内部两段合一（⚠️ 未实施，2026-10-10 复核后不建议按原写法做）

复核结论（原因，先看这里再动手）：

- **`_build_chunk_metadata` 的「concat 成一块再 narrow」是不安全的**：`chunk_indices` /
  `chunk_offsets` 是直接作为 kernel 入参的，长度数据相关；打包后每个 view 的
  `sizes.back()` 不再是整个 storage 的长度，exact-fit 规则失效，长度非 128 倍数时
  launcher 会每次多拷一份（量级与 §3.2.1 的 +20 µs 相同，甚至可能比它省的那一次 H2D 还贵）。
  只有把 `chunk_indices`/`chunk_offsets` 的拼接结果按 **固定上限**（`max_num_tokens // chunk + 1`
  取整到 128）预分配并在 device 上切片才安全，但 `prepare_chunk_indices/offsets` 的输出长度是
  动态的，需要额外 padding，改动量大于收益。
- **`compute_causal_conv1d_metadata` 的 `batch_ptr` / `token_chunk_offset_ptr`**：两段长度同为
  `MAX_NUM_PROGRAMS`（= `max(1024, mlist_len) * 2`，是 128 的倍数），理论上可以合到一条 storage
  的两个 view 上；但代码里有 `batch_ptr.nelement() < MAX_NUM_PROGRAMS` 的 `resize_()` 逻辑，
  view 不能 `resize_`，要改成「预分配 2×MAX 常驻 + 增长时重建 view」，且 `batch_ptr` 会被
  暴露给 FLA kernel（numel 语义要保持 `MAX_NUM_PROGRAMS`）。属于 vllm core 共享代码
  （`mamba_attn.py` / `short_conv_attn.py` / `kimi_k3/kda_metadata.py` 都在调），影响面大于收益。
- **收益仅 prefill**：这两处都在 `num_prefills > 0` 分支，decode 不走；每步 4 次 ≈ 0.18 ms，
  相对 prefill 的秒级耗时可以忽略。

→ 结论：不再按 §3.1 原方案实施；如后续要做，应按上面的「固定上限 + padding + view 重建」写法，
并单独立项（动 vllm core，需要回归其他 mamba 模型）。


两个函数都是「同一个 CPU 源 → 两个张量 → 两次 H2D」，改成「拼一块 → 一次 H2D → device 上切片」：

| 函数 | 现状 | 改法 | 每步 4→2 次 |
|---|---|---|---|
| `compute_causal_conv1d_metadata`（`backends/utils.py:1042`） | `mlist` → `batch_ptr`；`offsetlist` → `token_chunk_offset_ptr` | 分配一块 `[2*MAX_NUM_PROGRAMS]` pinned 源 + 一块 device 目标，两个字段各占一段；`nums_dict[...]["batch_ptr"]` 改成该 device buffer 的 `narrow` 视图 | 2 → 1 |
| `_build_chunk_metadata`（`gdn_attn.py:197-206`） | `async_tensor_h2d(chunk_indices)`、`async_tensor_h2d(chunk_offsets)` | 先 concat 成一块再 `async_tensor_h2d` 一次，然后 `split`/`narrow` | 2 → 1 |

注意：

- 两个函数的输出都会被 kernel 当**独立张量**用（`batch_ptr`/`token_chunk_offset_ptr` 是 kernel 入参），
  所以切片出来的视图必须满足 kernel 的连续性/对齐要求；`batch_ptr` 一族本来就是 `MAX_NUM_PROGRAMS`
  上限的定长 buffer，切段时按 `MAX_NUM_PROGRAMS` 对齐即可。
- `MAX_NUM_PROGRAMS` 变化时的 `resize_/fill_` 逻辑要保留（打包后总量按上限算）。
- 这两个函数都在 **capture 区外**执行，但打包 buffer 必须**常驻**（不要在捕获期 realloc），
  否则图捕获会退化。

预估收益：prefill 每步 −2 次 ≈ −0.09 ms（金额小，但改动也小、无风险）。
真正的价值是把它们统一进方案 2 的打包器，别再各自零散上传。

### 3.2 方案 2：`CpuGpuBuffer` 打包上传（收益最大）—— ✅ 已落地（2026-10-10，见 §3.2.2）

现状：`vllm/vllm/v1/utils.py:139` 的 `copy_to_gpu` 每个 buffer 各拷各的，而 DLC runner 每步要拷
4~6 个（§2.1）。它们有共同特征——**都是「小整型数组 + 固定上限（`max_num_reqs` / `max_num_tokens`）」**。

改法：

1. 在 `vllm_cl/worker/dlc_model_runner.py` 里加一个 `MetadataPacker`：
   - 一个常驻 pinned CPU buffer（`uint8`，按 `max_num_reqs`/`max_num_tokens` 预留，加载期分配）；
   - 一个同样大小的常驻 device buffer；
   - 一张段表 `{name: (dtype, capacity, count)}`。
2. 每步：把各 metadata 写进打包 buffer 的对应段 → **一次** `device_buf.copy_(packed_cpu, non_blocking=True)`
   → 对每个段 `narrow` 出视图，替换原来的 `self.xxx.gpu`。
3. 调用点（`§2.1` 的 `:1717/:1770`、`:1991`、`:2018`、`:2077/:2080/:2082`）从「各自 `copy_to_gpu`」
   换成「登记到 packer」，读侧仍是 `self.xxx.gpu[:n]`，语义不变。
4. 段表在构造时确定，段视图在构造时切好缓存，避免每步切片产生新的 Python 对象。

收益：把这 6~7 次（含 `logit_indices`）压到 1 次；按 44 µs/次算 ≈ **−0.3 ms/步**，prefill/decode 都受益。

#### 3.2.1 打包后段视图是否还需要「再分开连续化」——实测（2026-10-10，dlc:5）

疑虑（用户提出）：原先是各自独立的连续张量，打包进一条大 buffer 后，段视图会不会不再独立连续，
被 launcher/kernel 消费时又要单独连续化拷一份？

实测（`probes/probe_metadata_pack_cost.py`，真实 buffer 尺寸：`max_tokens=8192`、`max_reqs=256`）：

1. **段视图本身仍然是连续的**：按 512 B 对齐切段后，每个段的 `is_contiguous()==True`、
   `data_ptr()%512==0`、`storage_offset` 可能非 0；`.contiguous()` **返回自身，不产生任何拷贝**
   （Python 侧连续化是 no-op）。但请注意：`data_ptr()%512==0` **不是** launcher 的判定条件，
   launcher 看的是 `at::detail::is_contiguous_dlc`，见下条。

1b. **launcher「自动连续化」的真实判定（代码 + 实测）**——触发点
   `aten/src/ATen/dlc/DLCKernelLaunch.h:1046 _set_dlc_tensor_maybe_copy`：只有
   `KernelDesc::input()/output()`（format=`dlc_dlc_contiguous`）才会检查，不满足就
   `to_contiguous_dlc()` **实拷一份**（输入侧 post_fn 持引用、输出侧 post_fn `copy_` 回写）；
   `input_format(t)` 默认 `dlc_strided`，**完全不检查**。判定
   `aten/src/ATen/dlc/DLCTensorImpl.h:56 at::detail::is_contiguous_dlc` 依次为：

   1. `numel()==0` → true；
   2. `impl->is_contiguous()`（torch 语义连续）；
   3. `get_dlc_layout(dtype) == storage->dlc_layout_`（dtype 与 storage 布局必须一致）；
   4. `storage_offset % align == 0 && dlc_dim0_ % align == 0 && sizes.back() % align == 0` → true；
   5. 否则 `storage_offset % dlc_dim0_ != 0` → false；`dlc_dim0_ % align != 0` →
      `sizes.back() == dlc_dim0_`；否则 `sizes.back() % align == 0`。

   `align = dlc_storage_alignment()`（`c10/dlc/kernel_arg_types_copy.h:64`）：int8→**512**、
   int16→256、int32→**128**、int64→**128**，单位是**元素**（=512 B / itemsize），
   **不是字节**。所以「512 B 对齐」对 int64 只相当于 64 元素，远不够；真正的坑是第 4/5 条的
   `sizes.back() % align == 0`——**段内有效长度必须是 align 的整数倍**，光对齐起点没用。

   实测（`probes/probe_is_contiguous_dlc_rules.py`，dlc:6，`torch.add`）：

   | 段（dtype, numel） | 相对独占 buffer 的多余耗时 | 结论 |
   |---|---|---|
   | int32, 128 / 256 | ~0 | 判定连续，零拷贝 |
   | int32, **257** | **+20 µs（2.32x）** | 判定不连续，多一次实拷 |
   | int64, 128 / 256 | ~0 | 零拷贝 |
   | bool, 512 / 1024 | ~0 | 零拷贝 |

   真实 metadata 字段逐项：`query_start_loc`（int32, 257）**+19.6 µs**（触发拷贝）、
   `num_scheduled_tokens`(256) −0.5、`discard_request_mask`(bool,256) −0.9、
   `input_ids`(int32,8192) +0.15、`req_indices`/`query_pos`(int64,8192) +0.4~0.6（均无拷贝）。
   切片读法（模型真实 `buf.gpu[:n]`）同样会踩：`buf[257][:4]` +14.3 µs、`buf[257][:129]` +14.2 µs、
   `buf[8192][:4097]` +10.4 µs；只有 `buf[8192][:2048]` 恰好是 128 倍数才免拷（−1.3 µs）。

   本模型的对应字段（decode，`max_num_reqs=256`）：`max_num_reqs+1 = 257` 是**奇数**，
   按上面判定必然触发一次 ~20 µs 物化；`state_indices` 等 int32 字段段长也需按 128 元素（=512 B）取整。
2. **消费侧没有出现隐式物化**：已知能吃「大 buffer 连续切片」的 `torch.dlc_kda_state_gather`
   传入段视图与传入 offset-0 张量耗时一致（43270.3 vs 43271.1 µs，差 +0.8 µs）；通用 `torch.add`
   也没有变慢（噪声级，段视图那侧反而更快）。
3. **万一某个消费侧确实要独立张量，允许一次设备侧 `clone()`**，实测代价：

   | 字段 | nbytes | `clone()` | 它省掉的 1 次 H2D | clone/H2D |
   |---|---|---|---|---|
   | `query_start_loc` | 1028 | 21.9 µs | 39.1 µs | 0.56 |
   | `num_scheduled_tokens` | 1024 | 25.6 µs | 44.7 µs | 0.57 |
   | `discard_request_mask` | 256 | 24.4 µs | 44.2 µs | 0.55 |
   | `input_ids` | 32768 | 26.4 µs | 44.1 µs | 0.60 |
   | `req_indices` | 65536 | 25.7 µs | 63.0 µs | 0.41 |
   | `query_pos` | 65536 | 24.5 µs | 57.8 µs | 0.42 |

   `clone()` 是 **launch-bound（~22–26 µs，与大小无关）**，仍低于被省掉的那次 H2D（39–63 µs），
   而且省掉的是 host 侧下发（`synHostMalloc`/`driver.memcpy`/`backendPush`，正是造成 device 空转的部分）。
   **所以即使最坏情况下每个字段都要再物化一次，打包仍然净赚。**

设计约束（必须遵守，否则会把慢路径引进来）：

1. **段起点按 align 元素对齐、段长尽量取 align 元素的整数倍**：`align` 按 dtype 取
   （int8/bool→512、int16→256、int32/int64→128 元素），**不是统一的 512 B**；段内有效长度
   不是 align 整数倍时会触发 launcher 的一次实拷（见 1b）。注意：段容量 padding **不解决**
   消费侧切片的长度问题——kernel 拿到的是 `gpu[:num_reqs+1]`，其 `sizes.back()` 才是判据，
   所以 `query_start_loc` 这种 `max_num_reqs+1=257` 的字段必须**独立分配**（靠 exact-fit 规则
   免拷贝），实测塞进大 buffer 会从 27.4 µs 退化到 66.2 µs（见 §3.2.2）。
2. **按 dtype 分桶**：DLC storage 的 `dlc_layout_` 按 dtype 固定（`KDAStateGatherScatter.cpp` 的
   `check_storage` 会校验 `dlc_layout_ == dlc_padding_int32/int64/int8`），不同 dtype 不能塞进同一条
   buffer 再用 byte-view 切成别的 dtype。→ int32 一条、int64 一条、bool 一条。
3. 已知必须「独立物化」的是 `dlc_kda_recurrent_decode` 的 q/k/v/raw_g/beta（要求最内维 == storage
   最低维，见 `_fused_operand` 的注释），但那些是模型激活、不是本节的 metadata；`query_start_loc`
   那条路径本来就走 `.to(int32)+clone()`，不会因为打包变差。

风险与约束：

- `input_ids` 走的是 `CpuGpuBuffer` 的 `cpu`/`gpu` 双缓冲语义，改动时不要破坏
  `prev_sampled_token_ids` 的 scatter 路径（`:1785-1800`）。
- **图捕获**：vLLM 的 input buffer `gpu` 视图会被 cudagraph 直接引用；打包后必须保证视图
  `data_ptr` 稳定（常驻 device buffer + 固定 offset），否则会破坏捕获。建议先只打包
  metadata（非 graph input），把 `input_ids` 留到最后。
- 若 `enable_prompt_embeds`（多模态）打开，`inputs_embeds`/`is_token_ids` 体积大，不要并入打包，
  仍走单独 H2D。

#### 3.2.2 已落地实现（2026-10-10）

实现：新增 `vllm_cl/worker/metadata_packer.py`（`MetadataPacker` / `PackedSegment`），
在 `dlc_model_runner.py` 的 buffer 初始化处按 dtype 分桶分配常驻 pinned CPU + device buffer，
`_prepare_inputs` 里把生产者侧改成 `mark()` 登记、`flush()` 一次搬运。

| 字段 | 归属 | 说明 |
|---|---|---|
| `input_ids` | int32 桶（offset 0） | `_prepare_inputs` 的 index_select 后 `mark`，与 `num_scheduled_tokens` 一次 flush |
| `num_scheduled_tokens` | int32 桶（offset 8192，align 128） | 原 3 次 copy 合成 1 次 |
| `req_indices` | int64 桶（offset 0） | `_prepare_inputs` 与 `query_pos` 一起 flush |
| `query_pos` | int64 桶（offset 8192，align 128） | 同上 |
| `query_start_loc` | **独立**（`_make_buffer`，保持原样） | `max_num_reqs+1 = 257` 靠 exact-fit 规则免拷贝；实测塞进大 buffer 会退化成 66 µs vs 27 µs（2.42x） |
| `discard_request_mask` | **独立**（保持原样，bool align=512，`max_num_reqs=256` 也依赖 exact-fit） | — |

每步 H2D 次数：**6 → 4**（int32 桶 + int64 桶 + `query_start_loc` + `discard_request_mask`；
后两个是不同 dtype，无法再合。不含 async-spec / `num_accepted_tokens` 等分支各自的 copy）。

段在加入时即视为「未上传」，第一次 `flush()` 会无条件搬运整段——这样即使某个
生产者忘了 `mark()`，`PackedSegment` 也和 `CpuGpuBuffer` 一样不会读到陈旧数据。`_prepare_input_ids` 里原有的 `input_ids.copy_to_gpu(...)`
改成 `flush()`（幂等；数据已在 `_prepare_inputs` 随桶一起搬完，`prev_sampled_token_ids` 的
scatter 顺序不变）。

回退开关：`DLC_METADATA_PACK=0` → `MetadataPacker.add()` 直接返回普通 `CpuGpuBuffer`，
`mark/flush` 变成 no-op，行为与打包前完全一致。

验收：

- 单元测试 `tests/test_metadata_packer.py`（17 passed）：段偏移/容量按 align 取整、
  同 dtype 共享 storage、`flush()` 只搬脏段覆盖的最小连续区间、`copy_to_gpu/copy_to_cpu`
  往返、`isolated` 独立成桶、禁用开关。
- 真机探针 `probes/probe_metadata_packer_layout.py`（dlc:0）：打包后
  `input_ids[:128]/[:2048]`、`req_indices[:128]/[:2048]`、`query_pos[:128]/[:2048]`、
  `num_scheduled_tokens[:128]/[:256]` 与独立分配耗时比 0.96–1.16（= 无额外拷贝）；
  `[:2049]` 两侧都退化（0.96–1.11，本来就要拷）；`query_start_loc[:257]` 独立 27.4 µs、
  塞进大 buffer 66.2 µs（**2.42x**），确认必须 isolated。
- 真机数值核对（dlc:1）：写 `.np` + `mark` + `flush()` 后 device 各段值与 CPU 一致，
  且未越界污染相邻段。

### 3.3 方案 3：runtime 侧（P2-2）

即使合并后仍有几十次/步的拷贝（`input_ids`、`logits_indices`、metadata 分段等），
单次 44 µs 的固定成本最终由 runtime 决定。P2-2 已记：
`synHostMalloc` / `driver.memcpy` 随每次下发、`backendPush` 自旋。
这一项要 runtime 侧优化，插件侧只能减少次数。

### 4.3 微基准（不需要模型）

```python
# 复现 §1.2：逐个小张量 vs 合并成一次大拷贝（dlc:0，空闲卡）
import time, torch

dev = torch.device("dlc:0")
N, ROW = 900, 64

src = torch.arange(N * ROW, dtype=torch.int32).pin_memory()
big_dst = torch.zeros(N * ROW, dtype=torch.int32, device=dev)

# 逐个拷：900 次 256B H2D
rows = src.view(N, ROW)
for i in range(N):
    big_dst[i * ROW:(i + 1) * ROW].copy_(rows[i], non_blocking=True)
torch.dlc.synchronize(); t0 = time.perf_counter()
for i in range(N):
    big_dst[i * ROW:(i + 1) * ROW].copy_(rows[i], non_blocking=True)
torch.dlc.synchronize(); print("逐行:", (time.perf_counter() - t0) * 1e3, "ms")

# 合并拷：1 次 225 KB H2D（同样数据）
torch.dlc.synchronize(); t0 = time.perf_counter()
big_dst.copy_(src.view(-1), non_blocking=True)
torch.dlc.synchronize(); print("合并:", (time.perf_counter() - t0) * 1e3, "ms")
```

2026-10-09 实测：逐行 **39.9 ms**、合并 **0.10 ms**（≈400×）；单次平均 ≈44 µs，与 payload 无关。

## 5. 风险与注意

- 这些拷贝都在 forward 之外的 metadata 准备阶段，**不是**图捕获的前置阻塞；但打包 buffer 必须常驻，
  否则捕获期会新增分配。
- 合并后 `batch_ptr` / `chunk_offsets` 等从「独立张量」变成「大 buffer 的切片」，
  需确认 `is_contiguous()`、`data_ptr` 对齐（512 B 行）都满足算子侧校验。
- 若上游 vLLM 升级了 `compute_causal_conv1d_metadata` / `_build_chunk_metadata`，方案 1 的两处改动
  需要重新对齐（它们在 `vllm/` 里，不在 `vllm_cl/`；建议以 plugin patch 形式落地，便于随上游升级维护）。
- ✅ 2026-10-10：已确认 GLM-5 不再需要 `prefill.chunks`，回退开关与 `_kpool_prefill_chunks_enabled`
  已按本节建议删除（`patch_mla_indexer.py`），测试同步改为用 `_should_skip_glm5_prefill_chunks` 接缝覆盖
  其他模型的分块路径。
