# 集合通信「等同步」与「通信本体」的拆分（2026-10-10）

## 结论

1. **同事的猜测成立**：`allreduce` 占比大，主因不是 RDMA 传输，而是**等其它 rank 到齐**。
   - decode 单步：等同步 331.6 M cyc（118.3 ms），allreduce 本体 140.4 M cyc（49.8 ms）→ **sync : ring = 2.38 : 1**，即集合通信开销里 **约 70% 是空等**。
   - prefill 单步：等同步 346.5 M cyc（123.6 ms），本体 137.4 M cyc（48.7 ms）→ **2.54 : 1**。
2. **ring 本体各 rank 高度一致**（8 个 rank 都是 46.7–48.9 ms/步，单次 0.53–0.56 ms），说明传输路径本身没有慢 rank；而 sync 等待各 rank 差异极大（prefill 118.7–427.2 ms，rank0 最短、rank7 最长）→ **等待量 = 各 rank 到达屏障的时间差（skew）**。
3. 打开该开关后，集合通信**总开销反而下降**（decode 525.3 M → 472.0 M cyc，-10%；prefill 557.5 M → 483.9 M cyc，-13%）：显式对齐把原来混在 ring kernel 里的乱序等待提前吸收，ring 本体更干净。
4. 所有 kernel（含集合通信）都在**同一条 stream** 上，没有任何计算/通信重叠；decode 步设备繁忙 213.1 ms / 步跨度 602.6 ms（覆盖率 36%），prefill 273.5 ms / 1307.0 ms（21%）。**既然约 70% 的集合通信时间是在等，而设备又有 64–79% 的空闲，说明真正该做的是让等待与计算重叠，而不是优化 ring 带宽。**

## 方法

- 服务用 `start_glm5_flash_vllm_cl.sh --profile` 启动，脚本为此额外导出 `DLCCL_SYNC_ALL_MACHINE=1`
  （`DLC_CL/src/enqueue.cc:2135` 每次集合通信前插入 `custom_sync_all_machine`；`DLC_CL/README.md:517`）。
- 窗口：`POST /start_profile` → `/tmp/req_tiny_chat.json`（prompt 20 token，max_tokens=2）→ `POST /stop_profile`。
- 切窗：rank0 的 torch trace（`dp0_pp0_tp0_dcp0_ep0_rank0.1791594321997910397.pt.trace.json.gz`）
  的 `execute_context_*` user_annotation 作为 prefill / decode 窗口；DLCSynapse 设备 trace
  （`syn_trace_497087.json` … `syn_trace_497094.json`，pid 487087+rank = rank N）与 torch trace 同一 µs 时钟，按 ts 落入窗口聚合。
- **时钟标定**：不要用 1.4 GHz。窗口内 `sum(dur) == union(dur)`（单 stream、无重叠），
  用 `sum(cycles)/sum(dur)` 反推得 **2.92 GHz**；本文所有 cyc→ms 都按 2.92 GHz 换算，与 trace 自带 `dur` 一致。
- 每次集合通信的 `dur` 就是设备占用时间，且 sync/ring 首尾相接（173 对连续集合通信事件重叠数 = 0）。

## 对优化方向的影响

- **被证伪的做法**：继续调 ring 算法/带宽、加大 chunk——ring 本体只占集合通信时间的 30%，单次 0.55 ms，
  且 8 个 rank 完全一致，没有可挤的水分。
- **值得做的**：
  1. **让等待与计算重叠**：所有 kernel 都在同一条 stream 上，设备有 64–79% 空闲时间。把集合通信放到旁路 stream
     与后续独立计算（MoE/attention）重叠，理论上最多可回收 100+ ms/步。
  2. **削 skew**：prefill 侧 skew（>300 ms）比 decode（~50 ms）大得多，优先查 prefill 的 rank 间负载不均
     （KPool/MLA 的 host 编排、非 TP 分片的 indexer 都在 rank0 上）。
  3. **减少屏障次数**：87 次/步 × 1.31 ms 空等；能合并或消除的集合通信直接省等待，比省带宽收益大一个量级。
  4. **TP 8→4 的预期要下调**：ring 本体按跳数减半只省约 25 ms/步；收益主要来自 4 个 rank 的 max-skew 变小，
     属于「可能有用但要实测」，不再是主要理由（原本的 h16 kernel 缺失等约束仍然存在）。

## 追加：`custom_sync_all_machine` 到底在等什么（同一次采集的深化分析）

### 结论

1. **它在等其它 7 个 rank 到齐。** 把 87 个屏障逐个按 8 卡对齐后：**放行时刻（release）跨卡只差 0.040 ms（最大 0.149 ms）**，
   说明屏障本身是精确的；而**到达时刻（arrival）跨卡平均差 2.534 ms、中位 0.150 ms、最大 57.147 ms**。
   单卡等待 = 自己到达时刻到最后一个 rank 到达时刻的距离，所以「等同步」= **跨卡到达时间的差（skew）**，不是屏障慢。
2. **不是算力/工作量不均衡。** 把 sync 空转从设备繁忙时间里扣掉后，8 卡的**有效设备时间 94.3–95.9 ms（±0.8%）**；
   在偏斜最大的那几个段里，8 卡执行的是**同样 117 个 kernel、同样 1.89–1.91 ms 设备时间**（±0.5%）。
3. **差异全在 host 侧「同一批 kernel 发了多久」。** 同样 117 个 kernel，最快的 rank 用 15.7 ms 发完，最慢的用 29.8 ms，
   差出来的 14 ms 全是设备空转等 host。整个 decode 步：3888–3904 次下发、**3866 个下发空洞、平均每个空洞 0.098 ms、合计 379 ms（63%）**。
4. **可定位的最大单点抖动：阻塞式 D2H 读回。** 每步 11 个 indexer 层各一次 `rows.tolist()`
   （`vllm_cl/patch/models/kpool_indexer.py:773`，`_kpool_plans_without_host_reads` 的返回），
   host 侧每次阻塞 5–21 ms、首次数 93–124 ms；每卡每步在阻塞读回上合计 **184–254 ms**（占 602 ms 步长的 30–42%）。
   设备 trace 里对应的就是 `driver.memcpy`（`stream:0`，无 cycles），单次 13–21 ms——**几 KB 的读回却要十几 ms**，
   和之前 `zero_block_ids_pytorch` 的慢 D2H 是同一类现象。

### 证据

三步之内就能把「不是算力不均衡」钉死：

| 观测 | 数据 |
|---|---|
| 屏障放行时刻跨卡差 | 平均 0.040 ms，最大 0.149 ms |
| 屏障到达时刻跨卡差 | 平均 2.534 ms，中位 0.150 ms，最大 57.147 ms（87 次合计 220.5 ms） |
| 同一段 117 个 kernel 的设备时间 | 8 卡全部 1.89–1.91 ms（±0.5%） |
| 同一段的墙钟时长 | 15.711–29.766 ms（差异 100% 是设备空转） |
| 单步有效设备时间（busy − sync） | 94.3 / 95.9 / 95.5 / 94.6 / 95.8 / 94.6 / 94.3 / 95.3 ms |
| 单步阻塞式读回 | `tolist` 等 184–254 ms/卡（首个 93–124 ms） |

### 单步时间去向（decode，rank0 视角）

| 成分 | 时间 | 占比 |
|---|---|---|
| 有效设备计算 | 94.8 ms | 15.7% |
| 屏障上空等（等其它 rank） | 118.3 ms | 19.6% |
| 设备空转等 host（3866 个下发空洞） | 389.5 ms | 64.6% |

其中「设备空转等 host」里，小空洞是每次下发 ~100 µs 的固定开销（3888 次 ≈ 379 ms），
大空洞（>1 ms，共 7 个 16.9 ms）主要是 `.tolist()` / `.to()` / `.cpu()` 这些阻塞读回。

### 该怎么办

1. **删掉/搬到算子里**：`_kpool_plans_without_host_reads` 名义上「不读 host」，但最后一行 `rows.tolist()` 就是读回。
   让已提出的 KPool 融合算子直接吃这个 `[num_reqs, 7]` 计划张量（或让算子内部自己算），这 11 次 D2H 直接消失。
   若短期不能改，把 11 层合并成 1 次读回也能省 ~90%。
2. **降下发次数**：3888 次/步 → 379 ms 固定开销，是融合算子（少 kernel）最直接的收益点，比调 allreduce 带宽大一个量级。
3. **不要把 `custom_sync_all_machine` 当敌人**：它只是把原本藏在 allreduce 里的等待显式化（关掉它总开销反而更大），
   它测出的 arrival spread 就是「这一步各卡偏了多少」的现成指标（本窗口 220.5 ms/步）。
4. **图/异步下发**：既然单 stream、无重叠、host 主导，减少 host 参与（graph 捕获或把编排搬进算子）比任何通信优化都有效。

## 追加 2：rank 间 host 进度对齐实测与核/NUMA 绑定现状（2026-10-10）

上一层「追加」已经用 `custom_sync_all_machine` 测出**到达时刻跨卡差**；本节再做两件事：
① 直接对齐 8 个 rank 的 host 时间轴，判断「是不是某些 rank 的 host 处理速度系统性更慢」；
② 记录当前的 CPU / NUMA 绑定现状，作为「要不要做 NUMA 调优」的依据。

### 结论

1. **rank 之间没有系统性快慢，也没有累积漂移**：8 个 rank 的 prefill / decode 步边界对齐到 **<1 ms**，
   同一 decode 步的墙钟差只有 1–2%。屏障在每个集合通信点都会把各 rank 重新对齐，
   所以 host 侧的瞬时差异不会跨步累积。
2. **空等集中在少数屏障上，不是均匀分摊**：87 次屏障里 host 侧 `custom_sync_all_machine`
   的中位数只有 0.05–0.09 ms，p90 才 3–4 ms，极值 6–10 ms；>512 µs 的那几十次贡献了绝大部分合计时长。
   这与上一层「到达时刻跨卡差 中位 0.150 ms、最大 57.1 ms」一致。
3. 因此 Q2 的准确表述是：**每个 rank 的 host 在少数时刻会卡一下**（`tolist` D2H、`nonzero`/`item`、
   张量分配/GC、1.5k 次下发抖动），屏障把这个**瞬时差**放大成设备侧空等 ——
   而不是「某个 rank 的进程一直比别人慢」。
4. 即便 8 个 rank 的 host 完全等速且完全隔离，也只能消掉 sync 那一部分（decode ≈118 ms/步），
   动不了「设备空转等 host」的 389 ms/步 —— 那是 host **绝对速度**跟不上设备（设备繁忙覆盖率仅 36%）。

### 结论与决定

**已绑定 → NUMA 调优的空间比预期小。** 现有绑定已经把每个 rank 限定在一个 socket 内，
且 socket 没有被打满，所以「绑 NUMA」这件事基本已经做过；剩下能抠的只是
「socket 粒度 → 不重叠核组」这一档。

**本轮决定：不做 host 侧调优**，等算子交付。理由：

- 收益上限小：即便把 skew 完全消掉也只省下 decode ≈118 ms/步的 sync，
  而「设备空转等 host」的 389 ms/步 与 host **绝对速度**有关，绑核改变不了；
- 真正能同时消掉这两项的是 **D1 图捕获/预录**（host 整段移出关键路径），它一到位，
  瞬时卡顿、下发批大小（2.3 个/批）、屏障 skew 会一起消失，届时再评估是否还需要绑核。

**备选清单（记录在案，本轮不做）**，按性价比排序：

1. `KMP_BLOCKTIME=0` + 下调 `OMP_NUM_THREADS`：现为 18/worker × 4 worker/socket = 72 个 OMP 线程
   正好压满 72 个逻辑核，`KMP_BLOCKTIME` 默认 200 ms 会让空闲池继续自旋；
2. 每 worker 绑定**互不重叠**的物理核组（如 16–18 核），避免 4 个 worker 的线程在 socket 内互相迁移/抢占；
3. `kernel.numa_balancing=0`，pinned host buffer 用 `numactl --membind` 落本地 node；
4. CPU governor 由 `schedutil` 改 `performance`，消除调频抖动。
