## 4. 与 2026-10-09 对比（逐算子）

**结论：除集合通信外，每个算子的「次数 + cycles」与 10-09 完全一致（±1% 以内）**，
说明 workload、窗口切分与本指标口径可直接对比；差异全部落在集合通信上。

| 阶段 | 项 | 10-09 | 2026-10-10 | 变化 |
|---|---|---:|---:|---:|
| prefill | `custom_allreduce_ring_simple_bf16_rdma` | 468,954,046 | 69,843,713 | **−85.1%** |
| prefill | `custom_sync_all_machine` | —（未开） | 168,045,306 | 新增 |
| prefill | `custom_allgather_ring_simple_f32_rdma` | 8,075,179 | 374,092 | −95.4% |
| prefill | 集合通信合计 | 477,029,225（75.4%） | 238,263,111（60.6%） | **2.00×** |
| decode | `custom_allreduce_ring_simple_bf16_rdma` | 641,426,434 | 68,553,157 | **−89.3%** |
| decode | `custom_sync_all_machine` | —（未开） | 97,904,953 | 新增 |
| decode | `custom_allgather_ring_simple_f32_rdma` | 1,273,918 | 370,119 | −70.9% |
| decode | 集合通信合计 | 642,700,352（91.1%） | 166,828,229（72.7%） | **3.85×** |

其它需要留意的小差异：

- prefill `custom_convert_element_type_32bit` 262 → 194 次（cycles 4.02M → 3.80M）；
  `custom_reshape_offset_f32_off0` 925 → 923、`custom_reshape_offset` 315 → 313，
  都属窗口边界/多模态 profile 段的少量差异。
- 10-09 之后接入的 #05 / kpool 三件套 / sparse-attention / kda-chunk-prefill 等**没有改变**
  prefill+decode 的 kernel 组合（这些算子在 10-09 窗口里已经就位），因此本轮差异只有集合通信。

**待确认**：集合通信在「sync 开关」之外还有 ~2–4× 的额外下降。
10-10 的 torch-trace/设备 trace 结论是该开关只带来 ~10% 的收益，
因此这里还可能有第二个原因（例如 10-09 那次采集时卡片状态不佳，或期间更换过设备）。
建议做一次 **`GLM5_DLCCL_SYNC_ALL_MACHINE=0` 的同 workload kernel-log** 复现 10-09 口径，
即可把「开关收益」与「其它变化」分离。
