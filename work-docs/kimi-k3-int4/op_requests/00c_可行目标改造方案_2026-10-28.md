# Kimi-K3 可行目标改造方案（2026-10-28）

## 1. 可行目标定义

本方案的“可行目标”是：

1. V1 核心六个新算子都有实际计算，输出可直接进入下游计算；不接受纯 copy / reshape 算子。
2. 模型编排层不再出现冗余 `.copy_()`、`.contiguous()`、`torch.cat()` 和 D2H。
3. KDA/MLA 的 caller-provided 输出 buffer 在 capture/replay 中保持地址稳定。
4. 允许 attention、collective、paged cache gather 等算法内部必要的数据搬移。
5. graph 采用 vLLM 的 **breakable CUDA graph**：KDA/MLA 可作为可 replay 的 eager 段；
   不把“完整单 graph”作为首期验收条件。

在这个定义下，V1 可以先不改 DLC attention kernel 的 ABI；但 V copy 和 chunked-context
K concat 是否保留，必须作为明确例外记录，不能宣称已经零拷贝。

## 2. 总体改造顺序

```text
Step 0  API/workspace 契约
Step 1  #01 MoE + 去 D2H
Step 2  #05 SiTU + #02 AttnRes
Step 3  #04 MLA decode epilogue
Step 4  #03 MLA prefill epilogue + V copy 核查
Step 5  #06 KDA packed decode + 两处 copy 消除
Step 6  breakable graph 验证
Step 7  验收与回退开关
```

## 3. Step 0：API 与缓冲契约

### 3.1 统一输出参数

六算子均支持 caller-provided `out`/workspace：

- #01：`out=[T,3584]` BF16；routing/expert scratch 持久化；
- #02：`out=[T,7168]` BF16；
- #03：`out_k=[T,H,192]` BF16；
- #04：`out_mqa=[B,H,576]` BF16；
- #05：`out=[T,D]` BF16；
- #06：`out=[1,T,H,128]` BF16，可直接指向 `core_attn_out` slice。

禁止在 forward 里根据 device tensor 数值选择 shape 或执行 D2H。Top-k ids、state indices、
slot mapping、expert map 全部保持 device tensor。

### 3.2 回退开关

保留 native fallback，但默认走新算子：

- `DLC_K3_MOE_OP=kernel|native`
- `DLC_K3_MLA_EPILOGUE=kernel|native`
- `DLC_K3_ATTN_RES=kernel|native`
- `DLC_K3_SITU=kernel|native`
- `DLC_K3_KDA_PACKED=kernel|native`

开关只在初始化时读取，不能出现在每步分支里。

## 4. Step 1：MoE 热路径

### 修改点

1. `vllm_cl/ops/compressed_tensors_moe_native.py`
   - 将 `DLCNativeCompressedTensorsWNA16MoEMethod.apply` 的真实执行替换为 #01；
   - 删除 `topk_ids/topk_weights/expert_map` 的 `.to("cpu").tolist()`；
   - 保留 profile dummy fast path，但改成显式 profile context，不依赖 `load_format=dummy`；
   - native 循环仅作为 fallback。
2. `vllm-cl` 中为每层 MoE 预分配或复用 grouped-token scratch；不按 token 动态分配 Python 列表。
3. `KimiMoE` 的 latent down projection、shared experts、routed norm/up projection 和 all-reduce
   保持独立计算；不为了少 launch 融合成不必要的大算子。

### 验收

- profile / runtime 路径无 `.cpu()`、`.item()`、`.tolist()`；
- `T=1` 的 24 层 MoE 部分 ≤ 100 ms；
- 输出 `[T,3584]` 直接交给 all-reduce / RMSNorm / up-proj；
- graph capture 时 routing scratch 不改变地址。

## 5. Step 2：SiTU 与 AttnRes

### SiTU

- 在 `vllm_cl/ops/kimi_k3_native.py::DLCSituAndMul.forward_oot` 中调用 #05；
- 输出 `[T,D]` 直接给 `down_proj`；
- dense MLP 和 shared expert 共用同一实现；
- 不存在 `reshape`、`cat` 或 post-copy。

### AttnRes

- 用 #02 替换 `native_attn_res` 热路径；
- prefix/blocks 原位更新；
- `num_blocks`、`block_write_idx` 按 layer 固定，不能用 device tensor 驱动 Python 分支；
- 输出 `[T,7168]` 直接给 attention 或 MLP；
- 预留 `out` buffer，确保 breakable graph 前后 segment 输出地址稳定。

## 6. Step 3：MLA decode

### 修改点

1. `_decode_concat_cache` 调用 #04，不再走 native RoPE + `cat` + `index_copy_`。
2. #04 接收 `ql_nope` 的 strided bmm view，直接产出 `mqa_q=[ql_nope|q_pe]`。
3. `mqa_q` 直接交给 `TritonMLAImpl.forward_mqa` / `mqa_dlc`。
4. 缓存写入只修改 paged cache，不产生额外 device copy。
5. 若 `mqa_q` 需要跨 graph segment，使用 workspace buffer；否则可在同段内分配。

### 验收

- `B=1` decode epilogue ≤ 100 us；
- 无 `cat`/`index_copy_` 进入 profile；
- `mqa_q` 和 cache 数值与 native 对齐；
- 在 breakable graph 中 eager/graph 输出一致。

## 7. Step 4：MLA prefill

### 修改点

1. `_forward_prefill_fused` 调用 #03；q 原地 RoPE，K 输出直接给 DLC flash attention。
2. 现有 DLC `custom_flash_attention_varlen_GQA_bf16` 源码已经有
   `v_hbm0->storage_offset == 128 / stride[1] == 256` 的 offset-V 分支，理论上正好覆盖
   `kv_b_proj` 中 split 出来的 V view；先用真实 prefill shape 做 isolate probe。
   - 若 probe 通过：删除 `vllm_cl/patch/patch_mla_attention.py` 两处 `v.contiguous()`，
     该 copy 可在不新增 attention 算子的情况下消除。
   - 若 probe 不通过：V copy 必须保留并记录为 V1 已知例外；不要新增纯 copy 算子。
3. chunked-context K concat：
   - V1 可保留 native `fused_mla_kv_concat` 作为已知例外；
   - 若要求完整零拷贝，再新增 context attention 变体，直接消费 `k_nope/k_pe/v`，
     不单独提交 `cat` 算子；该 strict follow-up 已整理为
     [`#07`](07_dlc_kimi_k3_mla_context_attention_bf16.md)。

### 验收

- new-token prefill 的 q/K/cache 无模型层拷贝；
- 如果 `v.contiguous` 移除成功，profiler 里不再出现该 copy；
- 如果保留，文档和验收报告必须明确“MLA prefill 仍有 1 次 V 重排”。

## 8. Step 5：KDA packed decode

### 修改点

1. `vllm_cl/patch/patch_kda.py::fused_recurrent_kda_packed_decode_dlc` 直接调用 #06，
   删除 q/k/v `split`、`view` 和临时 `torch.arange` cu_seqlens。
2. `vllm/models/kimi_k3/nvidia/kda.py` 的普通 decode 把
   `core_attn_out` 的 slice 直接作为 #06 `out`，删除 `core_attn_out_non_spec -> core_attn_out` 拷贝。
3. KDA gated RMSNorm 改为双 buffer：
   - buffer A：KDA raw attention output；
   - buffer B：gated RMSNorm output；
   - 使用 `torch.dlc_kda_rmsnorm_sigmoid_gate.out(..., out=buffer B)`；
   - `buffer B` 直接进入 `o_proj`，不再 `.copy_()` 回 buffer A。
4. 为 `_forward` 增加/复用一个 caller-provided normalized output buffer，保证
   `@eager_break_during_capture` 的输出地址稳定。

### 验收

- 普通 decode 路径 profile 中不再出现上述两处 copy；
- `T=1` packed decode ≤ 100 us，18 层总成本 ≤ 2 ms；
- spec/mixed 分支仍使用 slice view，不能引入整块 copy；
- eager 与 graph 输出逐 token 一致。

## 9. Step 6：Breakable graph

1. 先 `--enforce-eager` 完成六算子数值验收。
2. 再启用 `--compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}'`，保留
   `VLLM_USE_BREAKABLE_CUDAGRAPH=1`。
3. KDA/MLA 的 `@eager_break_during_capture` 暂时不删除；先验证其 eager segment可 replay。
4. 必须保证：
   - KDA raw/norm output buffer 地址固定；
   - MLA `attn_out` 地址固定；
   - MoE route/workspace 地址固定；
   - AttnRes block/prefix 和 output buffer 地址固定；
   - 所有 attention metadata 在 capture/replay 间稳定。
5. prefill 仍保持 eager；若需要 prefill graph，另立里程碑，不与本轮混在一起。

## 10. 最终验收矩阵

| 检查 | 通过条件 |
|---|---|
| 有效计算 | 六算子均有真实计算，没有独立 `copy`/`reshape` 算子 |
| 模型编排 | 热路径不再出现 `.copy_()`、`.contiguous()`、`torch.cat()`、`.cpu()`、`.tolist()` |
| 数据形态 | 各算子输入/输出 shape 稳定；view 只做 stride/offset，不做 materialize |
| MoE | top-k / expert map 全 device；无 D2H |
| MLA decode | `ql_nope` strided 输入可用；mqa_q 直连 MQA |
| MLA prefill | q/k 直连 attention；V copy 已实测移除或有明确例外 |
| KDA | packed decode 直写 output；RMSNorm 双 buffer 无回拷 |
| AttnRes | prefix/blocks in-place；output 直连 attention/MLP |
| SiTU | `[T,2D] -> [T,D]` 直连 down GEMM |
| Graph | FULL_DECODE_ONLY + breakable graph；eager/graph 输出一致；无新增 D2H |
| 回退 | native/kernel 开关可切换，默认 kernel，故障可回退 |

## 11. 当前不建议做的事

- 不建议为 MLA context 单独新增“concat kernel”；它没有独立有效计算。
- 不建议为了凑单 graph 删除 KDA/MLA 的 eager break；先验证 replay 语义。
- 不建议在每层 forward 中根据 device tensor 数值做 Python 分支。
- 不建议把 shared expert、all-reduce、latent norm/up-proj 强行塞进 #01；它们是独立计算，
  只会扩大风险。
