# Kimi-K3 V1 核心六算子链式数据流审核（2026-10-28）

## 1. 审核问题

目标状态：

- 算子按真实模型顺序串联；
- 激活数据从上一个算子直接流到下一个算子；
- 不经过显式拷贝或形状变换；
- 编排代码少；
- 编排路径没有 CPU/device 同步；
- 可以开启 graph。

本页按真实模型代码审核 #01~#06 是否能共同达到该状态。

## 2. 总结论

**不能直接达到严格目标。**

原因有三类：

1. **不存在“六个算子串成一条链”的数据流。** 六算子属于多个并行/交替子图：
   - dense/shared MLP：GEMM -> #05 -> GEMM；
   - routed MoE：down_proj/router -> #01 -> all-reduce -> RMSNorm/up_proj -> shared add；
   - KDA：conv -> #06 -> gated RMSNorm -> o_proj；
   - MLA：projection/RMSNorm -> #03 或 #04 -> attention -> v_up/gate -> o_proj；
   - AttnRes：prefix/bank -> #02 -> attention 或 MLP。

   这些子图之间存在真实计算依赖，不能为了少 launch 强行串成单 kernel。

2. **算子实现正确不代表模型路径无拷贝。** 当前已知的显式拷贝：
   - MLA prefill 的 `v.contiguous()`；
   - KDA decode 结果拷贝到 `core_attn_out`；
   - KDA gated RMSNorm 结果再拷贝回 `core_attn_out`。

3. **当前 graph 能力没有证据达到“全路径单 graph”。** K3 的 KDA `_forward` 和 MLA
   `_attention` 仍使用 `@eager_break_during_capture`。这可以支持 breakable graph
   （graph 段 + eager 段 replay），但不是所有算子都在一个完整捕获 graph 中。

## 4. 具体阻塞点

### 4.1 MLA prefill 的 V copy

当前 `vllm_cl/patch/patch_mla_attention.py`：

```python
# run_prefill_new_tokens / run_prefill_context_chunk
v=v.contiguous(),
```

`kv_b_proj` 输出按 head 排列为 `[k_nope(128) | v(128)]`，`v` 是 strided view。
`.contiguous()` 是实际设备拷贝，占用了 MLA prefill 的额外 HBM 带宽。DLC GQA kernel
源码已经带有 `storage_offset=128 / stride=256` 的 offset-V 分支，因此先做真实 shape
probe；若 probe 通过，直接删除两处 `.contiguous()`，不需要新增 attention 算子。

仅实现 #03 不会移除该拷贝。必须二选一：

- 扩展 DLC flash attention 的 V ABI，接受 `(offset, row_stride, head_stride)`；
- 或在 kv_b_proj epilogue / MLA epilogue 中直接产出 attention 可消费的连续 V。

### 4.2 MLA chunked-context 仍有 native concat

`_compute_prefill_context` 对 context chunk 调用 `fused_mla_kv_concat`，当前 native
实现是 `torch.cat`，会分配并拷贝 K。它不在六算子范围内；严格零拷贝需要：

- 让 context attention 直接消费 `k_nope/k_pe` 两个视图；或
- 增加一个真正融合了 attention 前处理的 context kernel，见
  [#07](07_dlc_kimi_k3_mla_context_attention_bf16.md)。

单独的 `cat` kernel 不满足“每个算子有有效计算”的要求，不应作为独立需求提交。

### 4.3 KDA decode 后处理拷贝

当前 `vllm/models/kimi_k3/nvidia/kda.py`：

```python
core_attn_out[0, :num_actual_tokens] = core_attn_out_non_spec[0, :num_actual_tokens]
...
core_attn_out.copy_(self.o_norm(core_attn_out, g2))
```

#06 完成且 `out` 直接指向 `core_attn_out` 后，第一处可删除；第二处需改为
`torch.dlc_kda_rmsnorm_sigmoid_gate.out(..., out=core_attn_out)`，现有算子已有 `.out`
变体，不需要新 kernel。

### 4.4 Graph 当前状态

`vllm/models/kimi_k3/nvidia/kda.py::_forward` 和
`vllm/models/kimi_k3/nvidia/mla.py::_attention` 都带
`@eager_break_during_capture`。这意味着：

- 可以设计为 breakable graph：graph 段捕获其余计算，KDA/MLA 在 eager 段执行；
- 不能声称 KDA/MLA 已进入单张完整 graph；
- #01~#06 不改变该装饰器，也不自动保证 attention metadata、MoE route、all-reduce
  和 KDA/MLA eager 段都可 replay。

因此 graph 需要单独验收，至少包括：

1. `FULL_DECODE_ONLY` + breakable graph 启动；
2. 同输入 eager 与 graph 输出逐 token 一致；
3. 确认 KDA/MLA eager 段复用静态输入/输出 buffer；
4. MoE route 和 KDA state index 不触发 D2H。

### 4.5 AttnRes / SiTU

两者边界最干净：

- AttnRes 的 prefix 和 blocks 本身就是原位状态；输出直接作为 attention/MLP 输入；
- SiTU 的 `[T,2D] -> [T,D]` 直接作为 down GEMM 输入；
- 两者都不需要 reshape，也没有需要 D2H 的控制参数。

## 5. 为达到目标需要补的动作

### P0/P1 算子侧

- #01 必须接受 device 上的 `topk_weights/topk_ids`，内部预分配 scratch，禁止
  `.cpu().tolist()`，输出可由 caller 传入。
- #02/#04/#05/#06 均应支持 caller-provided `out`；#03 应至少支持 `out` 的 K 输出。
- #06 必须允许 `out` 直接指向 `core_attn_out` 的 `[1,T,H,Dv]` 视图。

### 模型接入侧

- 删除 KDA decode 的两处后处理拷贝：
  - `core_attn_out_non_spec -> core_attn_out`；
  - `o_norm(...) -> core_attn_out`，改用 RMSNorm `.out`。
- 删除 MLA prefill 的 `v.contiguous()`：扩展 attention V ABI，或新增真正的融合路径；
  不能把这部分伪装成“已经零拷贝”。
- chunked-context 的 K concat 要么直接消费 `k_nope/k_pe`，要么明确列为当前例外。

### 验证侧

- 为每个满足条件的子图记录 eager vs graph 输出一致性；
- profile 中确认没有 `Tensor.to(cpu)`、`.item()`、`.tolist()`、`.numpy()` 出现在每步路径；
- 确认所有显式拷贝已从 profile 中消失，或只剩不可融合的 collective/attention 内部搬移。

## 6. 审核结论

| 目标 | 结论 |
|---|---|
| 六个算子都有有效计算 | ✅ 除 #03 的部分路径仍依赖外部 V copy；其余均为真实计算 |
| 六算子形成一条无拷贝链 | ❌ 数据流是多子图，且 MLA prefill/KDA decode 仍有拷贝 |
| 后续编排代码很少 | ✅ 目标可达，但需要把 KDA/MLA 的 wrapper 简化，不是仅靠 kernel |
| 无 CPU/device 同步 | ⚠️ 新算子设计可做到；native MoE 当前仍有 `.to("cpu")`，必须替换 |
| 可以开启 graph | ⚠️ 可朝 breakable graph 设计，但当前不是完整单 graph，且尚未实测 |

最终建议：

1. 先按 #01~#06 实现算子。
2. 同步完成 KDA `.out` 接入和 MLA strided-V 能力。
3. 再把 `eager_break_during_capture`、attention metadata、MoE route、all-reduce 一起纳入
   graph 验收；在这些完成前，不要对外声称 K3 已实现“全路径零拷贝 graph”。
