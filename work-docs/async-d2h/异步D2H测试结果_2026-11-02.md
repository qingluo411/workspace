# DLC 异步 D2H 测试结果（2026-11-02）

测试目标：验证 PyTorch DLC 后端异步 D2H 的正确性、异步提交契约、生命周期保护，以及 vLLM 异步调度下的端到端效果。

## 结论摘要

- **PyTorch 侧 A/B/C 回归全部通过**：现有 D2H 测试、补充异步/生命周期测试、微基准均无失败。
- **微基准确认 B 组提交明显更早返回**：大拷贝控制积压中，A 组 submit 约 `5.97 ms`，B 组约 `0.053 ms`；B 的 event wait 约 `4.74 ms`，说明等待被移到了完成等待侧。
- **Qwen3-32B vLLM A/B 全部请求成功**：512/128、8 prompts、并发 1/8、每组 3 轮，所有请求 `failed=0`。
- **8 并发出现轻微正向信号**：B 组 output throughput 中位数约 `+3.0%`，TPOT p50 约 `-2.9%`；单并发没有稳定优势。
- **时间线已采集**：A/B rank0 trace 均通过 gzip 校验。B 组的 `dlcEventSynchronize` 集中在独立输出线程，A 组的主线程 `aten::_to_copy` 成本更高。
- **graph 模式未纳入本次有效结果**：当前 vllm-cl 的 Qwen3 fused-QKV patch 在 `FULL_DECODE_ONLY` 编译路径下不兼容；本次使用 `mode=none + cudagraph_mode=NONE`，保持非 eager 且 async scheduling 开启。

### 1.4 Qwen3 graph 模式说明

历史 FP8 Qwen3 实验使用 `--enforce-eager`，这会让 vllm-cl 关闭 async scheduling，因此不能用于 D2H 重叠验证。

本次有效测试使用 `mode=none + cudagraph_mode=NONE`、保持非 eager；`FULL_DECODE_ONLY` 路径暂时不纳入，因为当前 vllm-cl 的 `patch_qwen3.py` 在编译/graph 路径下会落到标准 `RotaryEmbedding.forward_native()`，而该接口不接受 fused-QKV 的 `qkv=` 参数。这是 Qwen3 patch 与 graph/compile 分派的问题，不是异步 D2H 的问题。

## 3. 异步提交与生命周期记录

### 3.1 控制积压

16M int32 单次 D2H，A/B 各一次控制积压记录：

| 组别 | submit | event wait | 返回时 pending |
|---|---:|---:|---|
| A fallback | 5.973679 ms | 0.084697 ms | true |
| B async | 0.053039 ms | 4.738049 ms | true |

A 组的 `pending` 仍可能为 true，不能单独用来判定 fallback；更可靠的证据是 A 的 submit 已包含同步 staging 开销，约比 B 慢两个数量级。B 组符合“提交后返回、等待完成”的契约。

- 所有轮次均无旧 DMA 覆盖新 pinned buffer，也没有提前释放导致的错误。

## 6. 代表性时间线

### 6.1 Trace 文件

A/B 均采集 short trace（32 input / 8 output、单请求），并复制到结果目录：

- `work-tests/async-d2h/results/qwen3-32b-trace-a-v2-20261102/traces/`
- `work-tests/async-d2h/results/qwen3-32b-trace-b-v2-20261102/traces/`

所有 rank0-3 和 frontend trace 均通过 `gzip -t`。采集时使用：

```json
{
  "profiler": "torch",
  "torch_profiler_with_stack": false
}
```

上一版带 stack 的 profiler run 在 `/stop_profile` 阶段超时，trace 不完整，已由 v2 替代。

### 6.2 rank0 事件摘要

| 事件 | A fallback | B async |
|---|---:|---:|
| `aten::_to_copy` 次数 | 48 | 48 |
| `aten::_to_copy` 总时长 | 20.520 ms | 2.738 ms |
| `aten::_to_copy` 最大单次 | 6.261 ms | 0.099 ms |
| `synMemCopyAsync` 次数 | 108 | 108 |
| `synMemCopyAsync` 总时长 | 1.694 ms | 1.918 ms |
| `dlcEventSynchronize` 次数 | 36 | 36 |
| `dlcEventSynchronize` 总时长 | 0.206 ms | 656.509 ms |
| `dlcEventSynchronize` 最大单次 | 0.053 ms | 99.610 ms |

### 6.3 时间线解释

A 组的 `aten::_to_copy` 在 worker 线程上承担了更大的同步成本，最大单次约 6.26 ms；B 组同一事件的提交路径降到最大约 0.10 ms。

B 组的长 `dlcEventSynchronize` 出现在独立线程（trace 中为 async output 线程），单次最长约 99.6 ms，说明 worker 主线程可以继续准备/提交下一批，而等待完成发生在输出侧。A 组的 event 等待很小，是因为大部分等待已经被同步 staging 吸收到了 `_to_copy` 内部。

这组 trace 支持“提交路径前移、完成等待线程化”的机制判断；由于 profiler 本身会放大时间，不把 trace 中的绝对时长当作端到端性能数字。

## 7. 结论与限制

### 已确认

- A/B/C PyTorch 回归、补充异步/生命周期测试和微基准全部通过。
- Qwen3-32B 在非 eager、no-graph、async scheduling enabled 配置下完成 A/B benchmark，所有请求成功。
- B 组的提交路径明显更短，event 等待出现在异步输出线程。
- 8 并发有轻微正向信号；单并发没有稳定收益。

### 未覆盖 / 限制

- 端到端只有 3 轮、512/128、单机 TP4，不能外推所有并发和长上下文。
- 时间线的绝对时长受 torch profiler 放大影响，只用于观察事件顺序和线程归属。
