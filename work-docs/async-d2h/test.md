| 测试 | 需要看到的结果 |
|---|---|

| **Host 内存生命周期** | 提交后丢弃 CPU 输出，再申请同尺寸 pinned buffer 并写入标记；新 buffer 不被旧 DMA 污染。记录压力轮数和同时在飞的拷贝数量。 |
| **Stream 与兼容性回归** | 默认／非默认 stream 在按契约建立依赖后结果正确；运行现有 H2D、DLC-to-DLC、Python dispatch、Autograd 和错误路径回归，保存通过、失败、跳过数量及原因。 |

异步测试有两个细节：

- **小拷贝返回时已经完成，并不能说明实现同步。** 应使用有界、受控的设备排队任务，让“提交”和“完成”有可观察的间隔。
- **CPU 数据校验必须在对应 event 完成后进行。** 提前读取异步 D2H 的结果可能得到未完成的数据；PyTorch 官方资料也明确说明了这一点。[异步拷贝说明](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html)

性能测试则要把三个问题分别测清楚。

**第一，主线程是否更早返回。** 微基准分别记录：

| 指标 | 计时边界 |
|---|---|
| 提交耗时 | 进入 `.to()` → `.to()` 返回，计时区间内不等待拷贝完成 |
| 数据就绪耗时 | 进入 `.to()` → 对应完成 event 等待结束 |
| 实际路径 | 是否命中新路径，是否仍发生 CPU unpack、额外 copy 或同步等待 |

两组采用相同输入和队列条件，预热后重复测量，保留原始值及中位数。**提交耗时缩短，不等于数据传输完成耗时按同样比例缩短。**

**第二，vLLM 是否获得了实际重叠。** 选一个已经稳定运行、确实启用异步调度的模型，保存 A／B 各一段代表性时间线，观察：

- worker 提交上一批 D2H 后，是否继续准备或提交下一批；
- 等待是否发生在预期的异步输出线程；
- D2H 与下一批 Host 工作、设备计算分别有没有重叠；
- 等待是否只是转移到了另一个关键路径位置。

“event 曾经 pending”只能支持异步完成关系，实际重叠需要时间线证明。

**第三，端到端是否受益。** 起步用一个固定请求集、固定输入／输出长度，测试单并发和一个常用并发档位即可。两组保持模型、精度、并行度、调度配置和预热方式一致，建议各重复至少 3 轮，记录：

- TTFT、TPOT，或逐 token ITL 的 p50／p95；
- 输出吞吐，单位为 output tokens/s；
- 输出正确性、失败／超时数量；
- 每轮结果和波动。

正式性能计时关闭 profiler 和逐次调试打印；另跑短时间线用于归因。logprobs、结构化输出、Speculative Decoding 可以放到扩展组，不必第一轮全部展开。

1. **版本、环境变量和完整测试命令。**
2. **测试通过／失败／跳过清单，以及失败详情。**
3. **异步提交与生命周期测试记录。**
